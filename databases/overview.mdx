Use Databases to keep structured content out of Git and in a typed table that your team, your partners, and your build pipelines can write to through one API. Mintlify hosts the data, validates every write against the columns, versions every record, and records every change so other systems can follow along.

Databases fit content that changes on a different cadence than your prose: a table of app versions that CI updates on every release, an app catalog maintained by external publishers, a partner directory that a sales team edits from the dashboard.

## How it works

A database belongs to one project. It has:

- **A slug.** Lowercase letters, digits, and underscores, such as `app_versions`. You address the database by its slug. Renaming the database changes its display name, not its slug.
- **Columns.** Each column has a name, a type, and the optional flags `required` and `indexed`. You address a column by its name, in any case.
- **Records.** Each record has an id, a `version` that increases on every write, and `fields` keyed by column name.
- **A change log.** Every write appends a change that you can read in batches or receive over a live stream.

You manage columns and records in the dashboard or through the [REST API](/databases/api). AI agents read them through the [admin MCP server](/databases/mcp). Rendering a database on a page with the [`<Database />` component](/databases/component) is planned.

## Limits

| Limit | Value |
| --- | --- |
| Columns per database | 100 |
| Indexed columns per database | 60 |
| Options per select column | 200 |
| Database and column name length | 120 characters |
| Record size | 2 MB of JSON |
| Records per upsert | 500 |
| Records per page | 100 |
| Filters per query | 20 |

A write that would exceed a limit returns an error and changes nothing.
