Every column has a name, a type, a position, and the flags `required` and `indexed`. Values are validated against the type on every write.

## Names

Records, filters, sorts, and SQL all refer to a column by its name. Names are matched in any case, so `release date` finds the `Release date` column. A name is unique within its database, up to 120 characters, and cannot look like a column id.

Each column also has a stable id of the form `col_` followed by eight characters. Paths and filters accept the id wherever they accept a name, and the change log uses it for a column that has since been deleted.

Renaming a column keeps every record's value. Records return the value under the new name from then on, so update any integration that sends the old name.

## Types

| Type | Write | Notes |
| --- | --- | --- |
| `text` | A string. | |
| `number` | A finite number, or a numeric string such as `"42"`. | Stored as a number. |
| `boolean` | `true` or `false`, or the strings `"true"` and `"false"`. | |
| `date` | A calendar date as `YYYY-MM-DD`. | Stored exactly as written. No time or time zone. |
| `datetime` | An ISO 8601 date-time, such as `2026-10-03T09:30:00+02:00`, or a date. | Normalized to UTC: `2026-10-03T07:30:00.000Z`. |
| `select` | One string. | See [select options](#select-options). |
| `multi_select` | An array of strings. | See [select options](#select-options). |
| `url` | An absolute `http` or `https` URL. | Other schemes are rejected. |
| `email` | An email address. | |
| `json` | Any JSON value, nested up to 64 levels. | Cannot be filtered, sorted, or indexed. |

Send `null` to clear a field. Dates that do not exist on the calendar, such as `2026-02-30`, are rejected rather than rolled over.

### `date` or `datetime`

Use `date` for a day that has no time attached, such as a release date. `2026-10-03` stays `2026-10-03` wherever the reader is. Use `datetime` for an instant, such as when a build finished. A `datetime` value always comes back in UTC.

## Select options

`select` and `multi_select` columns have a list of `options`, up to 200.

By default, writing a value that is not in `options` adds it as a new option. This suits a column such as `Platforms`, where new platforms appear as you write them.

Set `strict: true` to reject unknown values instead. Use it for a closed set, such as a `Channel` column that must be `stable` or `beta`, so a typo fails the write instead of creating a new option.

```json
{ "name": "Channel", "type": "select", "options": ["stable", "beta"], "strict": true }
```

`options` and `strict` apply only to select types. Sending either on another type returns `422`.

## Flags

### Required

A required column must have a non-null value on every record. Two rules keep existing records valid:

- You cannot add a required column to a database that already has records. Add it optional, backfill it, then set `required`.
- You cannot set `required` on a column while any record lacks a value. The error says how many records are missing one.

### Indexed

An indexed column is faster to filter and sort on. Index the columns you use in `where` and `sort`. A database can have up to 60 indexed columns. `multi_select` and `json` columns cannot be indexed.

## Change a column

[Update column](/api/databases/update-column) renames a column, moves it with `position`, or changes `required`, `indexed`, `options`, or `strict`. Moving a column renumbers the others so positions stay contiguous. A column's type cannot change: add a new column, copy the values, and delete the old one.

## Delete a column

[Delete column](/api/databases/delete-column) removes the column and its value from every record.

<Warning>
  Deleting a column cannot be undone. Export the records first if you might need the values.
</Warning>
