The editor [settings page](https://app.mintlify.com/settings/project/editor) controls the appearance, publishing behavior, and agent behavior.

- **Appearance**: Personal preferences for how the editor looks and behaves. These apply only to you.
- **Publishing**: Project-wide defaults for how the editor commits changes and opens pull requests. These apply to everyone who publishes. Admins and editors can update publishing behavior. On Enterprise plans, only admins can change **Auto publish**.
- **Reviewing**: Whether changes need approval before they publish, and the rules for approvals. Only admins can change reviewing settings.
- **Chat**: Persistent instructions for the editor's AI agent.
- **Danger zone**: Actions that can't be undone.

## Appearance

Appearance settings are personal preferences. They change the editor only for you and don't affect teammates or your published site. All appearance settings are off by default.

- **Fit editor to full width**: Stretch the editing canvas edge-to-edge instead of the default 768px column.
- **Show breadcrumbs**: Show the page's location in the site navigation above the editing canvas.
- **Open live preview in new tab**: When previewing, open the rendered page in a new browser tab.

## PR merge method

Select how the editor merges pull requests when you click **Merge and publish**:

- **Merge**: Creates a merge commit that preserves the full branch history. This is the default.
- **Squash**: Combines all commits in the branch into a single commit on your deployment branch.
- **Rebase**: Replays each commit from the branch onto your deployment branch without a merge commit.

<Tip>
  Match your merge method to your Git provider's branch protection settings. If your deployment branch only allows squash merges, set the method to **Squash** to avoid failed merges from the editor.
</Tip>

## Auto publish

Auto publish commits changes on your deployment branch automatically, about a minute after you stop editing. If you turn on this setting, the editor hides branches and the publish step for everyone on your site. Auto publish is off by default.

<Warning>
  With auto publish on, there is no pending state and no chance to review. Every edit reaches your live site shortly after you stop typing.
</Warning>

Turning on auto publish turns off [Require review before publishing](#require-review-before-publishing).

## Auto-create branches

When this setting is on and your deployment branch has branch protection, your first edit on the deployment branch creates a new branch and moves you onto it while you keep typing. The branch menu switches to the new branch, and a message tells you which branch your changes are on. Adding a comment doesn't create a branch. This setting is off by default.

You can't turn on this setting while your deployment branch has unpublished changes. Publish or discard them first.

If the editor can't create the branch, your edits stay on the deployment branch and a message tells you so.

## Create draft pull requests by default

When this setting is on, pull requests created from the editor open as drafts, including the pull request that opens after the first commit on a new branch. Authors click **Request review** to mark them ready when they finish editing. This setting is on by default.

If you want editor pull requests to open ready for review immediately, turn off draft pull requests.

## Add co-authors to commits

When this setting is on, each commit the editor makes lists everyone who made changes in that commit as a co-author. This includes the person who publishes and every teammate whose changes the commit includes. Git providers like GitHub then credit those people alongside the Mintlify bot. This setting is off by default.

Each co-author's name and email are visible to anyone who can see the repository. Co-authors don't need to connect a GitHub account. The editor uses the name on each person's Mintlify account. For the email, it uses their GitHub no-reply email address if they connected a GitHub account to Mintlify, and the email address on their Mintlify account otherwise.

Commits don't list deactivated members as co-authors.

## Show teammates' changes

Show teammates' changes controls whether the **Publish** menu lists your teammates' pending changes on your deployment branch.

<Note>
  This setting was previously called **Granular publishing**.
</Note>

- **Off (default)**: The **Publish** menu lists only your own changes. Select which of them to publish. Changes that only teammates made don't appear.
- **On**: The **Publish** menu also lists your teammates' pending changes, split into **Your changes** and **Modified by others**, so you can publish them too.

This setting only takes effect while you work on your deployment branch and that branch has no branch protections. See [Publish specific changes](/editor/publish#publish-specific-changes) for more information.

## Show all branches

Show all branches controls which branches the branch menu lists before you search.

- **Off (default)**: The branch menu lists your deployment branch, branches created in the editor, and branches with open or draft pull requests. Merged or closed branches and other branches in your repository only appear when you search for them by name.
- **On**: The branch menu lists every branch, including branches created outside the editor and merged or closed branches.

See [Manage branches](/editor/publish#manage-branches) for more information.

## Reviewing

<Info>
  Reviewing settings are in beta and require an [Enterprise plan](https://mintlify.com/pricing?ref=review) and a repository on GitHub.
</Info>

Only admins can change reviewing settings. The other reviewing settings take effect only while **Require review before publishing** is on, and admins can change them only while it's on.

### Require review before publishing

When you require review before publishing, only admins can publish changes directly to your deployment branch. Everyone else must request a review and reviewers must approve any changes before an admin or publisher can publish them. See [Require review before publishing](/editor/review#require-review-before-publishing) for how requests and approvals work. This setting is off by default.

- Requiring reviews before publishing turns off [auto publish](#auto-publish).
- If your deployment branch has branch protection, your repository must be on GitHub.com. Reviews then happen on branches, and admins can't publish without review. See [Review with a protected deployment branch](/editor/review#review-with-a-protected-deployment-branch).
- Reviews work on your deployment branch and on branches you create in the editor. On a branch, an admin or publisher can publish once reviewers approve every changed page. See [Review changes on a branch](/editor/review#review-changes-on-a-branch).

### Required approvals

Set how many reviewers must approve a change before it can publish, from 1 to 10. The default is 1. Each page needs that many approvals of its current version from reviewers on the request who can publish. The requester's own approval doesn't count, and each reviewer counts once. Review banners and the reviewers list in the **Publish** menu show progress, such as **1 of 2 approvals**.

If your deployment branch's GitHub branch protection requires more approvals than this setting, the setting says so.

### Dismiss approvals on new changes

When this setting is on, editing an approved page removes its approval, and the page needs another review before it can publish. This setting is on by default. It applies to review requests on your deployment branch.

When it's off, approved pages stay approved after later edits in the editor. Pages added to a request after approval still need approval. Pages that change in Git outside the editor still need another review. If your deployment branch's GitHub branch protection dismisses stale approvals, GitHub still dismisses them on new pushes, and the setting says so.

### Always require branches

When this setting is on, everyone except admins must publish their changes from a branch, even if your deployment branch doesn't have branch protection. For everyone else, Mintlify treats the deployment branch like a protected branch: they can't publish to it, and the **Publish** menu offers **Create branch** to move their changes to a new branch. Admins can still publish to the deployment branch directly. This setting is off by default.

### Sync with GitHub

When this setting is on, Mintlify copies **Required approvals**, **Dismiss approvals on new changes**, and **Always require branches** from your deployment branch's branch protection rules and rulesets in GitHub. Those settings show the values from GitHub, and you can't change them in Mintlify. When you change branch protection in GitHub, Mintlify picks up the change automatically. This setting is off by default.

When you turn on this setting, Mintlify reads your branch protection right away. If it can't, the setting stays off and you can try again. If Mintlify later can't read your branch protection, it keeps the last values it read and the setting says so.

If you turn off **Sync with GitHub**, you can change the settings again. They keep the last values copied from GitHub. You can turn off this setting even while **Require review before publishing** is off.

### Approve in Mintlify only

This setting works only when your repository is on GitHub.com and your deployment branch has branch protection. When it's on, reviewers approve changes only in Mintlify, and they don't need to connect a GitHub account. When an admin or publisher publishes approved changes, the Mintlify GitHub app merges the branch past your branch protection. This setting is off by default.

When this setting is off, every owner, admin, and publisher must [connect their GitHub account](/dashboard/profile#connect-github) before they can approve changes on your protected deployment branch.

Before you turn on this setting, add the Mintlify GitHub app to the bypass list of your deployment branch's protection in GitHub. In a ruleset, add the app to the bypass list. In classic branch protection, add it under **Allow specified actors to bypass required pull requests**. Until the app is on the bypass list, you can't turn on this setting. If the app loses its place on the bypass list after you turn on this setting, publishing approved changes fails until an admin adds it back.

## AI instructions

AI instructions are persistent guidance that the editor sends to the AI alongside your request. Use them to capture style and tone rules you don't want to repeat every time, like voice, terminology, or formatting conventions.

Your instructions apply to:

- **Agent sessions** started from the editor.
- **@mintlify** replies in [comment threads](/editor/collaborate).

Each teammate maintains their own instructions, scoped to their user account. Instructions are limited to 20,000 characters.

Add AI instructions when you find yourself repeating the same guidance in prompts, for example:

- Enforcing second-person voice or sentence case headings.
- Preferring specific product names or terminology.
- Banning marketing language or filler phrases.
- Requiring certain components, like always using `<Note>` for callouts.

Keep instructions short and specific. The AI follows them on every request, so vague or contradictory rules degrade results.

Example:

```text
- Use second person ("you") and active voice.
- Use sentence case for all headings.
- Refer to the product as "Acme"—never "Acme Inc." or "the platform".
- Wrap notes and warnings in <Note> or <Warning> components.
- Do not add introductory filler like "In this guide" or "Let's explore".
```

Leave the field empty to remove your instructions.

## Reset editor

**Reset editor** forces the editor to discard its local state and sync with your Git repository. After you confirm, the editor reloads. Admins and editors can reset the editor.

Reset the editor if it gets stuck out of sync with your repo, for example if the file tree is empty or shows errors like `Unable to find docs.json`. This can happen even though the file exists on your deployment branch and your live site builds normally.

<Warning>
  If you reset the editor, you discard any unpublished changes that you haven't committed to Git. If you have pending edits you want to keep, publish them first.
</Warning>
