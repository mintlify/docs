Preview your changes before they reach your live site, ask teammates to approve them, and publish or merge them from the editor.

## Choose a review setup

Your team can review changes in one of four ways. The setup you can use depends on your plan, where you host your repository, and whether your deployment branch has branch protection.

- **Publish without review**: Anyone who can publish sends changes straight to your deployment branch. This is the default. To publish automatically about a minute after each edit, turn on [auto publish](/editor/settings#auto-publish).
- **Review pull requests in your Git provider**: Teammates work on [branches](/editor/publish#work-on-a-branch), and reviewers approve each branch's pull request in GitHub, GitLab, or Bitbucket. On GitHub, reviewers who [connect their GitHub account](/dashboard/profile#connect-github) can also approve from the editor. To enforce reviews, add branch protection rules to your deployment branch in your Git provider. See [Review and merge pull requests](#review-and-merge-pull-requests).
- **Require review in the editor**: On Enterprise plans with a GitHub or GitLab repository, an admin can turn on [Require review before publishing](/editor/settings#require-review-before-publishing). Teammates request reviews and approve changes in the editor, on your deployment branch or on a branch. To make editors and publishers publish from a branch, also turn on [Always require branches](/editor/settings#always-require-branches). If your deployment branch doesn't have branch protection, admins can still publish without review. See [Require review before publishing](#require-review-before-publishing).
- **Require review with a protected deployment branch**: If your repository is on GitHub and your deployment branch has branch protection, turning on Require review before publishing moves every review to a branch. Admins can't publish without review, and GitHub's merge checks still apply. On GitHub.com, reviewers must connect their GitHub account to approve unless an admin turns off [Require connected GitHub account for reviewers](/editor/settings#require-connected-github-account-for-reviewers). On GitHub Enterprise Server, reviewers never need a GitHub account. See [Review with a protected deployment branch](#review-with-a-protected-deployment-branch).

When you require review, admins can set how many approvals a change needs and other rules with the [reviewing settings](/editor/settings#reviewing).

Who can approve and publish changes depends on your organization's [roles](/dashboard/roles). With [expanded roles](/dashboard/roles#expanded-roles), publishers and admins approve and publish changes, and editors request reviews.

## Live preview

Live preview renders your site as you edit, with no build step. With a page in **Navigation** open, click <Icon icon="play" /> **Preview** in the top bar. The preview opens full screen. Click **Refresh preview** to reload it, or **Close preview** to return to the editor. To open the preview in a new browser tab instead, turn on [Open live preview in new tab](/editor/settings#appearance).

To edit site settings and see how they affect your content, click **Site settings** in the preview toolbar, then select a configuration section.

To open the [agent](/editor/agent) beside the preview, click **Ask agent** in the preview toolbar. Only editors and admins can use the agent in live previews.

<Note>
  Live preview isn't available for sites that use standalone [personalization](/create/personalization) without authentication.
</Note>

## Preview deployments

<Info>
  Preview deployments require a [paid plan](https://mintlify.com/pricing?ref=preview-deployments). Restricting access to previews requires an [Enterprise plan](https://mintlify.com/pricing?ref=preview-deployments).
</Info>

When your feature branch has a pull request, Mintlify builds a preview deployment: a temporary URL where your changes render exactly as they look when published. The preview rebuilds each time the editor commits new changes to the branch. The URL combines your project's subdomain and the branch name: `<subdomain>-<branch-name>.mintlify.site`. Find the exact URL in the pull request comment from the Mintlify bot.

Preview URLs are publicly accessible by default. You can restrict access to members of your Mintlify organization with preview authentication in the **Previews** section of the [Site](https://app.mintlify.com/settings/project/site) page in your dashboard. See [Restrict access to preview deployments](/deploy/preview-deployments#restrict-access-to-preview-deployments) for more information.

## Which preview to use

| Feature | Live preview | Preview deployment |
|---|---|---|
| **Speed** | Instant | Requires a build |
| **Access** | Inside the editor | Shareable URL |
| **Use when** | Reviewing changes while editing | Sharing with your team for review |
| **Availability** | While the editor is open | As long as the branch exists |

## Share an editor link

To point a teammate at a specific page on a branch, click <Icon icon="ellipsis" /> **More options** in the top-right of the page, then click **Copy link**. Anyone with access to your Mintlify organization can open the link in their own editor session.

## Require review before publishing

<Info>
  Require review before publishing is in beta and subject to change. To require review before publishing, you must have an [Enterprise plan](https://mintlify.com/pricing?ref=review) and your project's repository must be on GitHub or GitLab.
</Info>

If an admin turns on [Require review before publishing](/editor/settings#require-review-before-publishing), changes on your deployment branch and on branches you create in the editor need a teammate's approval before an admin or publisher can publish them. Admins can publish their own changes without review, unless your deployment branch has branch protection.

On a branch, reviewers approve all changes on the branch at once in the editor. See [Review changes on a branch](#review-changes-on-a-branch).

### Request a review

1. Make your changes on your deployment branch or on a branch.
1. Click **Request review** in the top bar. This button replaces **Publish** when your changes need review.
1. In the **Request review** section, click **Choose reviewers** and select people or a group. You can only choose members who can approve changes.
1. Click **Request**.

The request includes every page you changed that isn't already in review. Each reviewer gets an email and an item in their [inbox](/dashboard/inbox).

Changes that don't belong to a page, such as navigation, site settings, and deleted files that aren't pages, go into the request as one **Site changes** item. Reviewers approve **Site changes** the same way as a page. Each uploaded file is its own item in the request.

While a page is in an open review request, the sidebar shows **In review** next to it. After a reviewer approves the page, the sidebar shows **Approved**.

Admins can publish without review on an unprotected deployment branch, but they can also request a review from the **Publish** menu.

### Review and approve changes

1. Open the review request from your inbox or email, or open a page that someone requested you to review.
1. Read the changes. Pages in the review open in diff view, including changes to the page title and description. In source mode, you see a text diff. To leave comments or suggestions instead of approving, use the [comment and suggestion tools](/editor/collaborate). Comments and suggestions don't approve or block a review.
1. Click **Approve** in the banner at the top of the page. Your approval applies to every page in the request.

If your project requires more than one approval, the changes can publish only after enough reviewers approve. The banner and the reviewers list in the **Publish** menu show progress, such as **1 of 2 approvals**. See [Required approvals](/editor/settings#required-approvals).

You can't approve your own review request.

To see a page without highlighted changes, click **Hide changes** in the toolbar. Click **Show changes** to bring them back. Your choice carries over to the other pages and to **Site settings** in the review.

If a review request contains only site changes and uploaded files, its banner appears in **Site settings** and on each uploaded file instead of on a page. Review links and inbox items for the request open **Site settings**.

To review site changes, open any changed section in **Site settings** and click **Show changes** in the top bar. Each field, such as the site name, primary color, or logo, shows its value before and after the change, compared with the branch your changes publish to. You can't edit the fields while changes show. Click **Hide changes** to go back to editing.

In the **Navigation** section, the tree marks added items in green, removed items in red, and changed items with their old and new values. Groups that contain changes show a dot, so expand them to see what changed.

To review changes to `docs.json`, open it in source mode and click **Show changes** in the top bar to see a read-only text diff. **Show changes** appears only during a review and only when `docs.json` has changes.

### Publish approved changes

When someone approves a review request, the requester gets an inbox item notifying them of the approval. Admins and publishers can publish the approved changes.

1. Open a page in the approved request.
1. Click **Publish** in the top bar. The **Publish** menu lists the requester's changes.
1. Click **Publish** followed by the requester's name, such as **Publish Ronan's changes**, then click **Publish** to confirm.

Only approved items publish. If a reviewer approved the request's **Site changes** item, the requester's navigation and site settings changes publish along with the approved pages.

If your approved navigation changes depend on unapproved changes in another open review request, such as moving a page into a group that the other request adds, those changes stay unpublished until someone approves or withdraws the other request. Your other approved changes still publish.

### Edit a page after approval

For review requests on your deployment branch, approved pages stay approved after you edit them in the editor, unless an admin turned on [Dismiss approvals on new changes](/editor/settings#dismiss-approvals-on-new-changes). Pages that change in Git outside the editor always need another review. For branches, see [Review changes on a branch](#review-changes-on-a-branch).

When **Dismiss approvals on new changes** is on, an approval applies only to the version of a page that the reviewer approved. If you edit, rename, or move an approved page, you must request a new review before publishing. When you start editing an approved page, the editor asks you to confirm with **Edit approved page?**.

Other approved pages in the same request keep their approval. Only the pages you changed need another review, and **Request review again** in the banner asks the reviewers to review just those pages.

The same applies to **Site changes** and uploaded files. If you change approved site changes or replace an approved file, the approval no longer applies. The banner shows **Request review again** so you can ask the reviewers to approve the new version.

### Add reviewers to a review request

To add reviewers to an open review request without withdrawing it, open the **Publish** menu, choose people or a group under **Reviewers**, and click **Request**. Existing approvals stay in place, and each new reviewer gets an email and an inbox item.

On your deployment branch, the requester and the request's reviewers can add reviewers. On a branch, any member except viewers can add reviewers to the branch's open request.

You can only add members who can approve changes. You can't add the requester or the person who created the branch.

### Withdraw a review request

To withdraw your review request before anyone approves it, open a page in the request and click **Withdraw** in the banner. For a request that contains only site changes and uploaded files, use the banner in **Site settings**.

To remove one reviewer from your request, open the **Publish** menu and click **Withdraw** next to the reviewer's name. Only the requester can remove reviewers. If you remove all reviewers, the request closes.

If you discard all changes in a request, the request closes.

A review request on a branch also closes on its own if someone merges the branch's pull request, closes it, or deletes the branch, including in GitHub. If the pull request merges into your deployment branch, the request closes as published. Otherwise, it closes as discarded.

If an admin turns off Require review before publishing, every open review request closes, and reviewers get an inbox item saying it was withdrawn.

### Review changes on a branch

When your project requires review before publishing, branches you create in the editor use the same review flow as your deployment branch. You request reviews and approve changes in the editor, and you don't see the branch's pull request. When you publish, the editor merges the branch into your deployment branch.

A review on a branch covers the whole branch. Every page of the branch shows one banner, such as **This branch is under review by** followed by the reviewers' names, and then **This branch is approved.** Clicking **Approve** in the banner approves the branch in one step.

- A branch publishes all at once. An admin or publisher can publish it only after reviewers approve every change on the branch. Then they click **Publish approved changes**, or **Publish changes** if the approval stayed in place after later changes. **Publish changes** also publishes those later changes.
- Changes to navigation, site settings, and other files that aren't pages go into the review as **Site changes**. Until a reviewer approves them, only an admin can publish the branch.
- Admins can publish a branch at any time.
- Anyone who can approve changes can approve a branch, except the person who created the branch and the person who requested the review.
- If you move or reorder an approved page, only that page needs another review. Adding a page or changing navigation doesn't affect the approvals on other pages.
- If [Dismiss approvals on new changes](/editor/settings#dismiss-approvals-on-new-changes) is off, the branch's approval stays in place after later edits and Git pushes, as long as the branch's pull request stays open. A new pull request needs a new approval.
- If **Dismiss approvals on new changes** is on and you edit the branch after approval, or someone pushes a change to it in Git, the banner shows **You edited this branch after it was approved** or **This branch changed in git after it was approved**. Click **Request review again** to ask the reviewers to review it again.
- Pages you delete on the branch are part of the review too. They appear as **Removed**, and reviewers approve them like any other page. A removed page's link in the review banner opens the page on your deployment branch in a new tab.
- If the branch no longer changes a requested page, the page leaves the review request.
- If the branch has a pull request, any approvals in the editor approve the pull request. If your repository is on GitHub.com and the reviewer [connects their GitHub account](/dashboard/profile#connect-github), Mintlify approves the pull request in GitHub as the reviewer. Otherwise, Mintlify adds a comment to the pull request with the reviewer's name and a link to the review request.
- Reviews that teammates leave on the branch's pull request in GitHub appear in the review request and in the [inbox](/dashboard/inbox) for reference. They don't count as approvals in the editor.
- If someone else published a change to the same part of a page, the branch has a conflict and you can't publish it until you resolve it. See [Resolve conflicts on a branch](#resolve-conflicts-on-a-branch).

On a [sub-branch](/editor/publish#sub-branches), the publish menu still shows **Publish to** your deployment branch and **Merge into** the parent branch.

### Resolve conflicts on a branch

If someone published a change to the same part of a page that your branch changes, the publish menu shows **Can't publish these changes** and disables **Publish**. The alert lists the conflicting pages. Click a page to see what someone published.

Conflicting pages show **Conflict** in the sidebar and a banner with **Resolve conflicts**. To resolve a page:

1. Click **Resolve conflicts** in the banner, or click the page in the publish menu.
1. For each numbered conflict, choose **Keep yours**, **Use published**, or **Keep both**. In source mode, you can also edit the result directly. Pages that can't show a visual diff open in source mode.
1. Click **Save**. To undo your choices on the page, click **Reset**.

When you save the last conflicting page, the editor updates your branch with your choices and the other published changes, and **Request review** comes back.

Your choices stay in this browser until you save, even if you reload the page. In another browser or on another device, you start over.

You can't resolve some files inside the page, such as renamed or deleted pages and files that aren't pages. For these, the publish menu offers a choice per file, such as keeping your version, using the published version, or deleting the file. After your last choice, click **Update branch** in the **Update this branch?** dialog.

If the conflict is in `docs.json`, ask an admin for help.

If the branch or the published version changes while you resolve, the editor asks you to choose again. Pages you resolve need another review, even if you keep your version. Approvals on other pages stay in place.

### Review with a protected deployment branch

If your deployment branch has branch protection, you can still require review before publishing when your repository is on GitHub.

On GitHub Enterprise Server, reviewers always approve in Mintlify without connecting GitHub, and the Mintlify GitHub app merges approved changes past your branch protection. The app must be on your deployment branch's bypass list, as described in [Require connected GitHub account for reviewers](/editor/settings#require-connected-github-account-for-reviewers).

<Note>
  On GitHub.com, unless an admin turns off [Require connected GitHub account for reviewers](/editor/settings#require-connected-github-account-for-reviewers), every owner, admin, and publisher must [connect their GitHub account](/dashboard/profile#connect-github) before they can approve changes.
</Note>

1. On your deployment branch, click **Create branch** to move your changes to a new branch.
1. Click **Request review** and choose reviewers. Mintlify opens the branch's pull request, or marks its draft pull request ready for review, then sends the review request.
1. Reviewers open the request from their inbox and click **Approve** in the editor.
1. After approval, an admin or publisher clicks **Publish approved changes**.

If a reviewer hasn't connected GitHub and your branch protection requires a GitHub approval, the editor asks them to connect their account before they can approve.

If an admin turned off [Require connected GitHub account for reviewers](/editor/settings#require-connected-github-account-for-reviewers), reviewers approve in Mintlify without connecting GitHub, and the editor doesn't ask them to connect. When an admin or publisher publishes, the Mintlify GitHub app merges the branch past your branch protection.

If **Dismiss approvals on new changes** is on, publishing merges only the version of the branch that reviewers approved, and edits after approval need another review. If it's off, publishing includes changes made after approval. GitHub's merge checks, such as required status checks, still apply.

With a protected deployment branch, admins can't publish without review. Approvals made directly in GitHub don't count as approvals in the editor.

## Review and merge pull requests

When your branch has a pull request, the publish menu shows its changed files and review status, like **Pull request created**, **Review required**, **Changes requested**, or **Approved**. If Mintlify hosts your repository, a draft shows **Draft in progress**. If your repository is in your own Git provider, such as GitHub, GitLab, or Bitbucket, click **View request** to open the pull request there.

<Tip>
  If the branch has unresolved comment threads, the publish menu shows a warning with the number of open comments in place of **Ready to publish** or **Approved**. You can still merge and publish. The warning reminds you to resolve feedback first.
</Tip>

On a feature branch, reviewers approve your pull request in your Git provider or, on GitHub, from the editor. If your project [requires review before publishing](#require-review-before-publishing), reviewers approve your changes in the editor instead. See [Review changes on a branch](#review-changes-on-a-branch).

1. Click **Publish** in the top bar, then click **Request review**. This marks the pull request ready for review.
1. Reviewers approve the pull request in your Git provider. If your repository is on GitHub and the pull request requires approval, reviewers can also click **Approve** in the **This branch needs a GitHub review** banner at the top of the page. To approve from the editor, a reviewer must [connect their GitHub account](/dashboard/profile#connect-github).
1. Click **Publish**, then click **Merge and publish**. The editor merges the pull request, deploys your changes, and switches you back to your deployment branch.

If Mintlify hosts your repository and approvals aren't required, the publish menu shows **Publish** instead, which merges and deploys in one step.

<Tip>
  Configure branch protection rules in your Git provider to require pull requests. See [About protected branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches) in the GitHub help or [Protected branches](https://docs.gitlab.com/user/project/repository/branches/protected/) in the GitLab help.
</Tip>

### Compare changes before merging

Click any changed file in the publish menu to open it in diff view against the published version. To leave diff view, click **Viewing changes** in the top bar. Visual mode shows a visual diff and source mode shows a text diff. Files that can't display a diff, such as images or deleted files, appear in the list but aren't clickable.

In a source mode diff of a page or `docs.json`, choose **Unified** or **Split** in the top bar to show changes in one column or side by side. Until you choose, the editor picks the layout that fits your window width. The editor remembers your choice for later diffs.

You can open [hidden pages](/organize/hidden-pages) that appear in the branch diff from the publish menu, even though they don't appear in your site navigation.

### Pull request titles and descriptions

The pull request title comes from your branch title.

If your branch has open comment threads, Mintlify adds a summary of them to the pull request description. See [Collaborate](/editor/collaborate#comments).

## Review an automation run

When an [automation](/automations) opens a pull request, click **View changes** in the Slack notification or notification email to open the editor on the automation's branch. The editor opens in diff view, and the [agent](/editor/agent#continue-an-automation-run) opens alongside it with context on what the automation did.

To open the automation's preview deployment instead, open the run from the **Runs** tab on the [Automations](https://app.mintlify.com/settings/project/automations?tab=runs) page of your dashboard, then click **Preview**.
