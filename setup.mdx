Your user wants Mintlify connected. Which half of this guide applies depends on one thing, so settle it before reading further.

## Answer this first: can you edit files on this machine?

**No, you're a hosted assistant** like Claude.ai or ChatGPT. You can't connect yourself. Adding a connector is a settings screen only your user can click. Don't try, don't apologize, and don't stop at "I can't do that." **Relay the instructions.** Say something close to this, as a numbered list:

> Mintlify connects as a connector. I can't add it myself, but it's two clicks for you:
>
> 1. Claude: open the [Mintlify connector](https://claude.com/marketplace/connectors/mintlify) and click **Connect**, or go to Settings → Connectors → Add custom connector. ChatGPT: install the [Mintlify app](https://chatgpt.com/apps/mintlify-mcp/asdk_app_6a4d5a687f0881918be3cb8b4b93773d).
> 2. For a custom connector, paste the server URL `https://mcp.mintlify.com` and approve the sign-in that opens.
> 3. **Claude: start a new conversation after adding the connector so the MCP tools become available.**
>
> On Claude there's a shortcut: [Connect to Claude](https://claude.ai/customize/connectors?modal=add-custom-connector&connectorName=Mintlify&connectorUrl=https%3A%2F%2Fmcp.mintlify.com) opens Add custom connector with Mintlify already filled in. Just confirm it.
>
> Tell me when it's done and I'll write your first page. If the tools don't show up, check the connector is switched **on** for this conversation. It can be added and still be disabled.

If they don't have a base yet, add one line before the list: "First create your base at [app.mintlify.com/signup?product=base](https://app.mintlify.com/signup?product=base)." Then stop. Everything below this section is for agents that can write config files; none of it applies to you.

**Yes, you're an AI coding agent** like Claude Code, Codex, Cursor, Antigravity or Grok Build. Do the setup yourself, verify it, and tell your user what you changed. Read on.

**Mintlify** hosts documentation sites and workspace pages. It exposes an MCP server, so once you're connected you get tools like `list_deployments`, `create_node`, `edit_page`, `publish`, and `manage_members_sharing`.

The one value that matters:

```
https://mcp.mintlify.com
```

It's a Streamable HTTP MCP server. It supports OAuth 2.0 with dynamic client registration and PKCE (`/.well-known/oauth-authorization-server`). The sign-in uses the person's Mintlify account; someone new to Mintlify creates their account in that sign-in.

## Keep messages to the person short

Each message says what's done and the one thing they do next, in two or three sentences. Don't relay what the CLI prints: no repository URLs, organization or project IDs, subdomains, file paths, timestamps, or tokens. Give a link only when they need to open it now.

## Ask what they're building

Before you configure anything, ask the person:

> Are you setting up a knowledge base for your team, or a public docs site?

### A knowledge base: a Mintlify base

A base is a private project for a team's internal knowledge: specs, runbooks, onboarding guides. It has no public site, no domain, and no GitHub setup. The person edits it in the Mintlify editor.

**New to Mintlify?** You create the base yourself with the CLI. The person needs no account until the last step, and you don't sign in. Don't run `mint login`, `mint new`, or plain `mint deploy`. From an empty directory, and running every `mint` command from it:

```bash
npx -y mint@latest deploy --base --subdomain <name>
```

It prints the editor link, when the base expires, and the next steps. Follow them in order:

1. **Clone it.** Run the clone command it prints. The base already has starter pages. The clone directory is the name the CLI printed, which gets a suffix if `<name>` was taken; use that directory below.
2. **Write and push.** Write the pages the person asked for in the clone, add each one to the navigation in `docs.json`, and commit. Then publish:

   ```bash
   npx -y mint@latest deploy --base --push <clone-directory>
   ```

   It rebases onto the latest `main` and pushes. Don't run `git push` yourself. Repeat for more changes.
3. **Claim it last.** A claimed base stops accepting pushes, so finish writing first. Don't ask for their email. Run `npx -y mint@latest claim` from the directory you deployed from, adding `--email <email>` only if you already know the email of their Mintlify account. Then tell them, and nothing more:

   > Your base is ready with [the pages you wrote]. Open this link, sign in with any account, and click Confirm: [claim link]
   >
   > It opens your base when you're done. Unclaimed bases are deleted in 24 hours.

   Leave out the repository, the organization and project IDs, the editor link, and the expiry timestamp. There is no code to relay and nothing more to run.

To keep editing it from this client after the claim, connect it with steps 1 to 4 below.

**Already in a Mintlify organization?** They add a base in the [dashboard](https://app.mintlify.com/): the project switcher → **New project** → **Base** → **Continue** → **Create project**. Then connect this client with steps 1 to 4 and write the first page (step 5). If they aren't sure whether they have one, connect first and check: `list_deployments` returns each project with a `projectType`, and a base is `"workspace"`.

### A public docs site

**Already in a Mintlify organization?** Run `npx -y mint@latest status` first. If it shows an organization, keep that session. If it doesn't and the person has an account, run `npx -y mint@latest login` in the background and have the person approve the sign-in in the browser. In a cloud or remote session, they run it in their own terminal. Their site deploys from the Git repository connected to their project, so don't run `mint deploy`: it creates a separate site, and claiming that site moves it into a new organization. Ask for the connected repository's URL, because `mint status` doesn't show it. Clone the repository, write the pages there, and push to the deployment branch. The push deploys the site.

**New to Mintlify?** Ask yourself a second question:

> Is git already set up in this folder? Are the docs nested inside a larger repository?

**Git is set up, including a monorepo with the docs in a subfolder.** From the repository root, with the GitHub CLI signed in:

```bash
npx -y mint@latest deploy --github --subdomain <name> --directory <docs-directory>
```

Leave out `--directory` when `docs.json` is at the root. The command needs a `docs.json` in the docs directory, an `origin` remote on github.com, and the GitHub CLI (`gh`) signed in with access to the repository.

- If the repository has no `docs.json` yet, create the docs in a new, empty subdirectory with `npx -y mint@latest new <docs-directory> --name "<Project name>" --theme mint`, then pass that subdirectory with `--directory`.
- If the repository is on another host, such as GitLab, run `npx -y mint@latest deploy --subdomain <name>` from the directory with `docs.json` and follow the steps under "Git isn't set up." After the person claims the site, they connect their repository in the dashboard's Git settings.

`deploy --github` trusts the repository to deploy the site and writes `.github/workflows/mintlify.yml`. Commit the workflow on a new branch and open a pull request with `gh pr create`. Once it merges, the GitHub Action deploys the site on every push to the default branch.

**Git isn't set up.** Start a new docs site, then publish it:

```bash
npx -y mint@latest new docs --name "<Project name>" --theme mint
cd docs
npx -y mint@latest deploy --subdomain <name>
```

`mint deploy` prints the site URL, a hosted Git repository, a write token, and the clone and push commands to run. Run them, and pass the token only as the per-command header the output shows. Never put it in a remote URL, a file, Git config, or a message to the person. The token lasts about 10 minutes; if it expires, run `mint deploy` again from the same directory for a fresh one. The site is deleted after 24 hours unless the person claims it. [auth.md](https://www.mintlify.com/auth.md) has the full walkthrough.

**Then claim the site and add a custom domain.** Don't ask for their email first. From the same directory, run:

```bash
npx -y mint@latest claim
```

If you already know the email of their Mintlify account, add `--email <email>` to prefill the sign-in. Give them the claim link it prints. They sign in with any account and click **Confirm**, and the site moves into a new organization in their account. There is no code to relay. Then ask which domain the docs should live on. `add-domain` needs a signed-in CLI. On the person's own machine, run `mint login` in the background and tell them to approve the sign-in in the browser it opens; then run `add-domain`. In a cloud or remote session, the browser can't reach this machine, so the person runs both commands in their own terminal:

```bash
npx -y mint@latest login
npx -y mint@latest add-domain docs.example.com
```

`add-domain` prints the DNS records they add at their DNS provider.

If you published through [auth.md](https://www.mintlify.com/auth.md) without the CLI, you don't need `mint login` for the domain. After the claim, follow its "Add a custom domain" step with your agent credentials. Give the person the `TXT` records first, then the `CNAME` to `cname.mintlify.builders` once they validate. To serve the site under `/docs` on a domain that hosts another site, tell them to set up a [reverse proxy](/deploy/docs-subpath) instead of the `CNAME`.

To edit the site from this client afterwards, connect it with steps 1 to 4.

## Can nobody sign in from here?

MCP OAuth needs a person at the client: on Claude Code that is `/mcp` → **Authenticate**, typed by them, in an interactive session. A **non-interactive** run (`claude -p`, CI, a scheduled job, an SDK script) or a **cloud session** (Claude Code on the web, a routine) can't do that, so the server shows "needs authentication" and its tools never load.

- **For a new base or a public docs site**, the `mint` CLI creates and publishes it with no account at all and works inside a session that is already running. Follow "A knowledge base" or "A public docs site" above.
- **For an existing base**, the MCP server is the only way in. Relay the connector setup below to the person and stop.

### Cloud sessions (Claude Code on the web, routines)

The VM is fresh every session and reads none of the person's own machine: not `~/.claude.json`, not their plugins, not a shell profile. So `claude mcp add --scope user` sets up nothing that lasts. Don't try it. What makes Mintlify work here is set by the person, once, on claude.ai; relay one of these two and stop:

- **The connector**, for a base or a docs site. claude.ai Settings → Connectors → Add custom connector, paste `https://mcp.mintlify.com`, approve the sign-in, and enable it for the session. Or hand them this link, which opens that dialog prefilled: [Connect to Claude](https://claude.ai/customize/connectors?modal=add-custom-connector&connectorName=Mintlify&connectorUrl=https%3A%2F%2Fmcp.mintlify.com). Connector traffic goes through Anthropic, so no network setting is needed. The tools appear in the next session.
- **The CLI**, for a new base or a public docs site. Open the cloud environment's settings and set **Network access** → Custom, with the hosts listed in [auth.md](https://www.mintlify.com/auth.md) for a sandbox with a network allowlist, and "Also include default list of common package managers" checked so `npx` still reaches npm. Then, in a new session, follow "A knowledge base" or "A public docs site" above.

Before calling a sign-in broken, read Mintlify's public sign-in metadata. JSON that starts with `{"issuer"` means the network lets Mintlify through; a proxy page or a connection error means the network setting:

```bash
curl -sS https://mcp.mintlify.com/.well-known/oauth-authorization-server | head -c 120
```

## Ground rules

- **Read before you write.** These config files hold the user's other MCP servers. Read the file, add or update only the `mintlify` entry, keep everything else byte-for-byte, and confirm the result parses before moving on. If the file already exists, back it up first.
- Say which file you're about to touch before you touch it.
- **Don't ping Mintlify to see if it answers.** A status-only `curl` (`-o /dev/null -w '%{http_code}'`, `curl -I`, `curl -sI`) against a host your user didn't name is what Claude Code's auto mode calls _Exfil Scouting_, and it blocks the command. Nothing here needs one: the sign-in and the first real call are the test.

## Step 1: use OAuth

If the client supports MCP OAuth, the URL alone is enough: the client opens a browser, the user approves once, and the client manages the OAuth credentials. Claude Code, Codex, and Cursor support this. There is no API key to set.

## Step 2: configure this client

Work out which client you're running inside. If you can't tell, ask. A config written to the wrong path fails silently.

### The shortcut: Claude Code, Codex, and Cursor at once

On the user's own machine (a shell you can run commands in, Node.js 22.20+ but not 25), one command installs the Mintlify skill and adds the `mintlify` server for Claude Code, Codex, or Cursor. Name the agent you are:

```bash
npx -y mint@latest agent setup --global --agent claude-code
```

- Always pass `--agent` (`claude-code`, `codex`, or `cursor`; repeat it for more). Without it, a run with no terminal configures every agent it finds on the machine.
- Each agent's config gets one `mintlify` entry pointing at `https://mcp.mintlify.com`. It doesn't sign in: each agent still does its own OAuth sign-in in step 4.
- It prints the file it changed per agent and the sign-in step for each; relay both.
- **If Claude Code blocks it in auto mode**, tell the user what the command does and let them decide.

Use the per-client sections below when there's no shell on the user's machine, the user wants only this one client, or `agent setup` left a client alone.

### Claude Code

In a cloud session or a non-interactive run, skip this section: nothing here can finish there. Use "Can nobody sign in from here?" above.

```bash
claude mcp add --transport http --scope user mintlify https://mcp.mintlify.com
```

> **Required after installation:** Restart your Claude session (exit and run claude again, or start a new terminal) for the MCP server and tools to take effect.

**If Claude Code blocks the command, that's expected. Don't fight it.** In auto mode, Claude Code's safety classifier stops an agent from adding an MCP server on a web page's say-so, and this is a web page. The block is the classifier doing its job, so:

- don't retry;
- don't route around it, since hand-editing `~/.claude.json` is the same action it just refused;
- tell the user what the command does and let them decide. Say it plainly ("Claude Code won't let me add an MCP server on my own in auto mode. This line adds the Mintlify server; run it yourself if you want it"), and if they do, go on to step 4 for the restart and sign-in.

Pass `--scope` explicitly. It defaults to `local`, which pins the server to the current directory only. That's usually not what "set this up for me" means. Use `--scope user` for "available everywhere" (stored in `~/.claude.json`), and `--scope project` only if it should be shared with everyone who clones this repo (that writes `.mcp.json`, which is committed).

Confirm it registered before you do anything else:

```bash
claude mcp get mintlify
```

The browser sign-in happens after the restart, in step 4. It's driven by the `/mcp` command, which only the user can type; you can't run it for them.

To undo the whole thing: `claude mcp remove mintlify --scope user`.

If you must write JSON by hand, the file is `~/.claude.json` for user scope (top-level `mcpServers`) or `.mcp.json` in the project root for project scope. It is **not** `~/.claude/settings.json`. That file doesn't read `mcpServers`, and Claude Code ignores a config placed there.

```json
{
  "mcpServers": {
    "mintlify": {
      "type": "http",
      "url": "https://mcp.mintlify.com"
    }
  }
}
```

`"type": "http"` is required. An entry with a `url` and no `type` is treated as a stdio server and errors.

### Cursor

The user can do it in one click instead of you editing a file: hand them the [Mintlify plugin](https://cursor.com/marketplace/mintlify), which adds the server and the Mintlify skill, or [Add to Cursor](https://cursor.com/en/install-mcp?name=mintlify&config=eyJ1cmwiOiJodHRwczovL21jcC5taW50bGlmeS5jb20ifQ%3D%3D), which opens Cursor's install prompt with this entry filled in. They confirm it, then sign in from Cursor's MCP settings.

To write it yourself: `~/.cursor/mcp.json` (global) or `.cursor/mcp.json` (project). Default to global unless the user wants it shared with the repo:

```json
{
  "mcpServers": {
    "mintlify": {
      "url": "https://mcp.mintlify.com"
    }
  }
}
```

Cursor handles OAuth, so leave auth out entirely.

### Codex

On the user's own machine, prefer the CLI and OAuth. Check for an existing entry with `codex mcp get mintlify`; if it already points at the URL below, reuse it. Otherwise, add the server:

```bash
codex mcp add mintlify --url https://mcp.mintlify.com
```

This saves the server in Codex's user configuration (`$CODEX_HOME/config.toml`, default `~/.codex/config.toml`) and starts OAuth automatically. Open the printed authorization URL in the user's browser if it does not open itself. Keep the command running while the user signs in and approves, then check that it reports `Successfully logged in.` before claiming authentication succeeded.

For an existing entry, or to retry an incomplete sign-in:

```bash
codex mcp login mintlify
```

Verify the saved URL and enabled state:

```bash
codex mcp get mintlify
```

Configuration, authentication, and tool availability are separate checks. If this task does not have the tools yet, start a new Codex task; reload the client if needed. Then run `list_deployments` to verify an authenticated tool call. This connection is local to Codex on this machine; it does not add a ChatGPT connector. ChatGPT needs the separate hosted-assistant setup above.

To undo: `codex mcp remove mintlify`.

**Manual configuration:**

```toml
[mcp_servers.mintlify]
url = "https://mcp.mintlify.com"
```

Then run `codex mcp login mintlify`. Preserve all other servers and settings.

On a remote or headless machine, do not send the user a loopback OAuth link: its callback returns to the machine running Codex. For a base, have the person connect Codex on their own machine; for a public docs site, use the CLI path in this guide instead.

### Antigravity (CLI and IDE)

Both read one shared file, `~/.gemini/config/mcp_config.json` (or `.agents/mcp_config.json` in a project, for that workspace only). Read it first, since it holds the user's other servers, and add only the `mintlify` entry:

```json
{
  "mcpServers": {
    "mintlify": {
      "serverUrl": "https://mcp.mintlify.com"
    }
  }
}
```

The key is `serverUrl`. Antigravity ignores `url` and `httpUrl` for remote servers, so an entry copied from the Claude Code or Cursor shape above loads as nothing, silently. Leave auth out: Mintlify supports dynamic client registration, which Antigravity uses to run the OAuth sign-in by itself.

To finish, the user opens the `/mcp` panel (a slash command they type, not you), reloads if Mintlify isn't listed yet, and completes the browser sign-in; the server shows **Authed** next to its name when it worked.

### Grok Build

Grok Build reads Claude Code's MCP config, so if `.mcp.json` or `~/.claude.json` already has the `mintlify` entry there is nothing to do. Otherwise:

```bash
grok mcp add --transport http mintlify https://mcp.mintlify.com
```

### Hosted assistants (Claude.ai, ChatGPT)

Covered at the top of this guide. Relay the steps to your user. There's no config file to write.

### Any other MCP client

Add it however that client adds a remote Streamable HTTP MCP server, with OAuth.

### The CLI, for CI and any agent with a shell

The CLI creates and publishes new bases and public docs sites with no account and no sign-in: `mint deploy --base` or `mint deploy`, then a claim. If the person wants either, there is nothing to configure in this client; follow "A knowledge base" or "A public docs site" above.

This is also the way **you** publish when the MCP server isn't connected yet, or isn't authorized: it works inside a session that is already running, with no restart and no `/mcp`.

**Run `mint login` only on the person's own machine.** It opens a browser and waits until the person approves there or pastes a code back. Run it in the background and tell them to approve. In a cloud or remote session the browser sign-in can't return to this machine, so the person runs it in their own terminal. Of the steps in this guide, only `add-domain` needs it.

**If Claude Code's auto mode blocks `npx -y mint@latest`, ask; don't work around it.** Don't retry on your own, and don't swap in another way to run it. Tell them in one line what it does ("Auto mode won't run the Mintlify CLI from npm on my own; reply _yes, run it_ and I'll publish the site") and, once they have, run the same command once. Write the docs before you ask, so nothing waits on the answer but the publish.

## Step 3: verify what you can before restarting

The restart ends your session, so check everything checkable now.

Whichever client you configured, re-read the file you wrote and confirm it parses and contains the entry you intended. On Claude Code, `claude mcp get mintlify` does this for you; on Codex, use `codex mcp get mintlify`.

## Step 4: hand off across the restart

New MCP configurations may need a fresh session to load. On Codex, start a new task and reload the client if needed; on other clients, restart or reload. **A new base or public docs site doesn't have to wait for it.** Ship it with the CLI above and let the restart be a separate errand. An existing base waits for the restart. Before they restart, tell them in one message:

1. the file you changed, and how to undo it;
2. that they need a new task on Codex, or a restart on other clients. Then they sign in: on Claude Code they type `/mcp` themselves and pick **Authenticate** (a slash command is user input; an agent can't send it), on Codex they run `codex mcp login mintlify`, on Cursor they connect it in MCP settings. Someone new to Mintlify creates their account in that sign-in;
3. that afterwards they should ask their agent to **run `list_deployments`** to confirm the connection. A base shows `projectType: "workspace"`.

Three ways it goes wrong, and what each one means:

- **The tools aren't there at all.** The client never read the config. Re-check the path for that client, confirm the file parses, and confirm the restart actually happened. On Claude Code, also check `--scope`: a `local`-scope server only exists in the directory it was added from.
- **The server is listed, no browser prompt appears, and calls say auth is required.** Automatic OAuth discovery didn't kick in. Have the user run `/mcp` and choose Authenticate explicitly on Claude Code, or run `codex mcp login mintlify` on Codex.
- **The tools are there but every call is an auth error.** The grant didn't complete. Redo the browser approval.

## Step 5: offer a first page

Then offer to write something, since that's the fastest way to see what was just connected:

```
Write a one-page overview of this project in Mintlify and send me the editor link
Turn this week's changes into release notes in Mintlify
```

`create_node` with `visibility: "private"`, `parentId: null`, and `data: { type: "page", path, title, content }` writes the page and returns an `editorUrl`. Send the person that link; it opens the page in the Mintlify editor. Tool arguments and the access model are documented in [Admin MCP server](/ai/mintlify-mcp).

## Something here wrong or broken?

Report it from where you are, no browser or sign-in needed. From a shell:

```bash
npx -y mint@latest feedback "setup step 2 failed: …" --client-id setup-report-001 --category bug
```

`--category` is `bug`, `docs`, or `idea`. Pick a fresh `--client-id` per report. The report goes to the Mintlify team. Leave keys and other secrets out of the message.
