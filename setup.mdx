Your user wants Mintlify connected. Which half of this guide applies depends on one thing, so settle it before reading further.

## Answer this first: can you edit files on this machine?

**No—you're a hosted assistant** (Claude.ai, ChatGPT). You cannot connect yourself: adding a connector is a settings screen only your user can click. Don't try, don't apologize, and don't stop at "I can't do that." **Relay the instructions.** Say something close to this, as a numbered list:

> Mintlify connects as a connector—I can't add it myself, but it's two clicks for you:
>
> 1. Claude: open the [Mintlify connector](https://claude.com/marketplace/connectors/mintlify) and click **Connect**, or go to Settings → Connectors → Add custom connector. ChatGPT: install the [Mintlify app](https://chatgpt.com/apps/mintlify-mcp/asdk_app_6a4d5a687f0881918be3cb8b4b93773d).
> 2. For a custom connector, paste the server URL `https://mcp.mintlify.com` and approve the sign-in that opens.
> 3. **Claude: start a new conversation after adding the connector so the MCP tools become available.**
>
> On Claude there's a shortcut: [Connect to Claude](https://claude.ai/customize/connectors?modal=add-custom-connector&connectorName=Mintlify&connectorUrl=https%3A%2F%2Fmcp.mintlify.com) opens Add custom connector with Mintlify already filled in—just confirm it.
>
> Tell me when it's done and I'll write your first page. If the tools don't show up, check the connector is switched **on** for this conversation—it can be added and still be disabled.

Then stop. Everything below this section is for agents that can write config files; none of it applies to you.

**Yes—you're an AI coding agent** (Claude Code, Codex, Cursor, Antigravity, Grok Build): do the setup yourself, verify it, and tell your user what you changed. Read on.

**Mintlify** hosts documentation sites and workspace pages. It exposes an MCP server, so once you're connected you get tools like `list_deployments`, `create_node`, `edit_page`, `publish`, and `manage_members_sharing`.

The one value that matters:

```
https://mcp.mintlify.com
```

It's a Streamable HTTP MCP server. It supports OAuth 2.0 with dynamic client registration and PKCE (`/.well-known/oauth-authorization-server`). The sign-in uses the person's Mintlify account; someone new to Mintlify creates their account in that sign-in.

## Can nobody sign in from here? Publish with the CLI

MCP OAuth needs a person at the client: on Claude Code that is `/mcp` → **Authenticate**, typed by them, in an interactive session. A **non-interactive** run (`claude -p`, CI, a scheduled job, an SDK script) or a **cloud session** (Claude Code on the web, a routine) can't do that, so the server shows "needs authentication" and its tools never load. That is not a dead end. The `mint` CLI publishes with no account at all, and works inside a session that is already running. Follow "Publish with the CLI" below.

### Cloud sessions (Claude Code on the web, routines)

The VM is fresh every session and reads none of the person's own machine: not `~/.claude.json`, not their plugins, not a shell profile. So `claude mcp add --scope user` sets up nothing that lasts. Don't try it. What makes Mintlify work here is set by the person, once, on claude.ai; relay one of these two and stop:

- **The connector.** claude.ai Settings → Connectors → Add custom connector, paste `https://mcp.mintlify.com`, approve the sign-in, and enable it for the session. Or hand them this link, which opens that dialog prefilled: [Connect to Claude](https://claude.ai/customize/connectors?modal=add-custom-connector&connectorName=Mintlify&connectorUrl=https%3A%2F%2Fmcp.mintlify.com). Connector traffic goes through Anthropic, so no network setting is needed. The tools appear in the next session.
- **The CLI.** Open the cloud environment's settings and set **Network access** → Custom, with the hosts listed in https://www.mintlify.com/auth.md under Allowed domains, and "Also include default list of common package managers" checked so `npx` still reaches npm. Then, in a new session, follow "Publish with the CLI" below.

Before calling a sign-in broken, read Mintlify's public sign-in metadata. JSON that starts with `{"issuer"` means the network lets Mintlify through; a proxy page or a connection error means the network setting:

```bash
curl -sS https://mcp.mintlify.com/.well-known/oauth-authorization-server | head -c 120
```

## Publish with the CLI: ask what they're building

Before you run `mint deploy`, ask the person:

> Are you setting up a knowledge base, or a public docs site to host?

`mint deploy` prints the site URL, a hosted Git repository, a write token, and the clone and push commands to run. The site is deleted after 24 hours unless the person claims it. https://www.mintlify.com/auth.md has the full walkthrough, including the claim.

### A knowledge base (Mintlify base)

Provision a new site and work in the hosted Git repository it gives you, even if the current folder already has git:

```bash
npx -y mint@latest deploy --subdomain <name>
```

Clone the repository it prints into a new directory and write the pages there. Every push to `main` deploys to production. For a fresh write token, run `mint deploy` again from the directory you first ran it in.

### A public docs site

Ask a second question:

> Is git already set up in this folder? Are the docs nested inside a larger repository?

**Git is set up, including a monorepo with the docs in a subfolder.** From the repository root, with the GitHub CLI signed in:

```bash
npx -y mint@latest deploy --github --subdomain <name> --directory <docs-directory>
```

Leave out `--directory` when `docs.json` is at the root. It trusts the repository to deploy the site and writes `.github/workflows/mintlify.yml`. Commit the workflow on a new branch and open a pull request with `gh pr create`. Once it merges, the GitHub Action deploys the site on every push to the default branch.

**Git isn't set up.** Start a new docs site, then publish it:

```bash
npx -y mint@latest new docs --name "<Project name>" --theme mint
cd docs
npx -y mint@latest deploy --subdomain <name>
```

Run the clone and push commands `mint deploy` prints.

**Then claim the site and add a custom domain.** Ask for the email address that should own the site, never invent one, and claim it:

```bash
npx -y mint@latest claim --email <email>
npx -y mint@latest claim --code <code>
```

Give them the claim link the first command prints; run the second with the code they read back. Then ask which domain the docs should live on and add it. `add-domain` needs a signed-in CLI, so the person approves `mint login` first:

```bash
npx -y mint@latest login
npx -y mint@latest add-domain docs.example.com
```

`add-domain` prints the DNS records the person adds at their DNS provider.

## Ground rules

- **Read before you write.** These config files hold the user's other MCP servers. Read the file, add or update only the `mintlify-admin` entry, keep everything else byte-for-byte, and confirm the result parses before moving on. If the file already exists, back it up first.
- Say which file you're about to touch before you touch it.
- **Don't ping Mintlify to see if it answers.** A status-only `curl` (`-o /dev/null -w '%{http_code}'`, `curl -I`) against a host your user didn't name is what Claude Code's auto mode calls _Exfil Scouting_, and it blocks the command. Nothing here needs one: the sign-in and the first real call are the test.

## Step 1—use OAuth

If the client supports MCP OAuth, the URL alone is enough: the client opens a browser, the user approves once, and the client manages the OAuth credentials. Claude Code, Codex, and Cursor support this. There is no API key to set.

## Step 2—configure this client

Work out which client you're running inside. If you can't tell, ask—a config written to the wrong path fails silently, which is the worst outcome here.

### The shortcut: Claude Code, Codex, and Cursor at once

On the user's own machine (a shell you can run commands in, Node.js 22.20+), one command configures Claude Code, Codex, and Cursor, whichever are installed here:

```bash
npx -y mint@latest agent setup --global
```

- It adds the `mintlify-admin` server to each agent's config and installs the Mintlify skill where each agent reads skills.
- It prints what it changed per agent; relay that list. A config it can't parse is named: configure that one agent by hand below.
- Each agent still signs in once on its own (step 4).
- To configure only some agents, pass them: `--agent claude-code`, `--agent codex`, `--agent cursor`.
- **If Claude Code blocks it in auto mode**, tell the user what the command does and let them decide.

Use the per-client sections below when there's no shell on the user's machine, the user wants only this one client, or `agent setup` left a client alone.

### Claude Code

In a cloud session or a non-interactive run, skip this section: nothing here can finish there. Use "Can nobody sign in from here?" above.

```bash
claude mcp add --transport http --scope user mintlify-admin https://mcp.mintlify.com
```

> **Required after installation:** Restart your Claude session (exit and run claude again, or start a new terminal) for the MCP server and tools to take effect.

**If Claude Code blocks the command, that's expected—don't fight it.** In auto mode, Claude Code's safety classifier stops an agent from adding an MCP server on a web page's say-so, and this is a web page. The block is the classifier doing its job, so:

- don't retry;
- don't route around it—hand-editing `~/.claude.json` is the same action it just refused;
- tell the user what the command does and let them decide. Say it plainly ("Claude Code won't let me add an MCP server on my own in auto mode. This line adds the Mintlify server; run it yourself if you want it"), and if they do, go on to step 4 for the restart and sign-in.

Pass `--scope` explicitly. It defaults to `local`, which pins the server to the current directory only—usually not what "set this up for me" means. Use `--scope user` for "available everywhere" (stored in `~/.claude.json`), and `--scope project` only if it should be shared with everyone who clones this repo (that writes `.mcp.json`, which is committed).

Confirm it registered before you do anything else:

```bash
claude mcp get mintlify-admin
```

The browser sign-in happens after the restart—see step 4. It's driven by the `/mcp` command, which only the user can type; you can't run it for them.

To undo the whole thing: `claude mcp remove mintlify-admin --scope user`.

If you must write JSON by hand, the file is `~/.claude.json` for user scope (top-level `mcpServers`) or `.mcp.json` in the project root for project scope. It is **not** `~/.claude/settings.json`—that file does not read `mcpServers`, and a config placed there is silently ignored.

```json
{
  "mcpServers": {
    "mintlify-admin": {
      "type": "http",
      "url": "https://mcp.mintlify.com"
    }
  }
}
```

`"type": "http"` is required. An entry with a `url` and no `type` is treated as a stdio server and errors.

### Cursor

The user can do it in one click instead of you editing a file: hand them the [Mintlify plugin](https://cursor.com/marketplace/mintlify), which adds the server and the Mintlify skill, or [Add to Cursor](https://cursor.com/en/install-mcp?name=mintlify-admin&config=eyJ1cmwiOiJodHRwczovL21jcC5taW50bGlmeS5jb20ifQ%3D%3D), which opens Cursor's install prompt with this entry filled in. They confirm it, then sign in from Cursor's MCP settings.

To write it yourself: `~/.cursor/mcp.json` (global) or `.cursor/mcp.json` (project). Default to global unless the user wants it shared with the repo:

```json
{
  "mcpServers": {
    "mintlify-admin": {
      "url": "https://mcp.mintlify.com"
    }
  }
}
```

Cursor handles OAuth, so leave auth out entirely.

### Codex

On the user's own machine, prefer the CLI and OAuth. Check for an existing entry with `codex mcp get mintlify-admin`; if it already points at the URL below, reuse it. Otherwise, add the server:

```bash
codex mcp add mintlify-admin --url https://mcp.mintlify.com
```

This saves the server in Codex's user configuration (`$CODEX_HOME/config.toml`, default `~/.codex/config.toml`) and starts OAuth automatically. Open the printed authorization URL in the user's browser if it does not open itself. Keep the command running while the user signs in and approves, then check that it reports `Successfully logged in.` before claiming authentication succeeded.

For an existing entry, or to retry an incomplete sign-in:

```bash
codex mcp login mintlify-admin
```

Verify the saved URL and enabled state:

```bash
codex mcp get mintlify-admin
```

Configuration, authentication, and tool availability are separate checks. If this task does not have the tools yet, start a new Codex task; reload the client if needed. Then run `list_deployments` to verify an authenticated tool call. This connection is local to Codex on this machine; it does not add a ChatGPT connector. ChatGPT needs the separate hosted-assistant setup above.

To undo: `codex mcp remove mintlify-admin`.

**Manual configuration:**

```toml
[mcp_servers.mintlify-admin]
url = "https://mcp.mintlify.com"
```

Then run `codex mcp login mintlify-admin`. Preserve all other servers and settings.

On a remote or headless machine, do not send the user a loopback OAuth link: its callback returns to the machine running Codex. Use the CLI path described in this guide instead.

### Antigravity (CLI and IDE)

Both read one shared file, `~/.gemini/config/mcp_config.json` (or `.agents/mcp_config.json` in a project, for that workspace only). Read it first—it holds the user's other servers—and add only the `mintlify-admin` entry:

```json
{
  "mcpServers": {
    "mintlify-admin": {
      "serverUrl": "https://mcp.mintlify.com"
    }
  }
}
```

The key is `serverUrl`. Antigravity ignores `url` and `httpUrl` for remote servers, so an entry copied from the Claude Code or Cursor shape above loads as nothing, silently. Leave auth out: Mintlify supports dynamic client registration, which Antigravity uses to run the OAuth sign-in by itself.

To finish, the user opens the `/mcp` panel (a slash command they type, not you), reloads if Mintlify isn't listed yet, and completes the browser sign-in; the server shows **Authed** next to its name when it worked.

### Grok Build

Grok Build reads Claude Code's MCP config, so if `.mcp.json` or `~/.claude.json` already has the `mintlify-admin` entry there is nothing to do. Otherwise:

```bash
grok mcp add --transport http mintlify-admin https://mcp.mintlify.com
```

### Hosted assistants (Claude.ai, ChatGPT)

Covered at the top of this guide—relay the steps to your user; there is no config file to write.

### Any other MCP client

Add it however that client adds a remote Streamable HTTP MCP server, with OAuth.

### The CLI—for CI, and for any agent with a shell

If the person wants a knowledge base or a docs site published from a terminal, a script, or on every git push, there is nothing to configure in this client. Follow "Publish with the CLI" above: ask what they're building, then whether git is set up.

This is also the way **you** publish when the MCP server isn't connected yet, or isn't authorized: it works inside a session that is already running, with no restart and no `/mcp`. Reach for it instead of telling someone their site has to wait.

**If Claude Code's auto mode blocks `npx -y mint@latest`, ask; don't work around it.** Don't retry on your own, and don't swap in another way to run it. Tell them in one line what it does ("Auto mode won't run the Mintlify CLI from npm on my own; reply _yes, run it_ and I'll publish the site") and, once they have, run the same command once. Write the docs before you ask, so nothing waits on the answer but the publish.

## Step 3—verify what you can, before restarting

The restart ends your session, so check everything checkable now.

**Config shape**—whichever client you configured, re-read the file you wrote and confirm it parses and contains the entry you intended. On Claude Code, `claude mcp get mintlify-admin` does this for you; on Codex, use `codex mcp get mintlify-admin`.

## Step 4—hand off across the restart

New MCP configurations may need a fresh session to load. On Codex, start a new task and reload the client if needed; on other clients, restart or reload. **Publishing does not have to wait for it**—if there is a site to ship now, ship it with the CLI above and let the restart be a separate errand. Before they restart, tell them in one message:

1. the file you changed, and how to undo it;
2. that they need a new task on Codex, or a restart on other clients, and then—on Claude Code—type `/mcp` themselves and pick **Authenticate** to do the browser approval (a slash command is user input; an agent can't send it). Someone new to Mintlify creates their account in that sign-in;
3. that afterwards they should ask their agent to **run `list_deployments`** to confirm the connection.

Three ways it goes wrong, and what each one means:

- **The tools aren't there at all**—the client never read the config. Re-check the path for that client, confirm the file parses, and confirm the restart actually happened. On Claude Code, also check `--scope`: a `local`-scope server only exists in the directory it was added from.
- **The server is listed but no browser prompt ever appears, and calls report that auth is required**—automatic OAuth discovery didn't kick in. Have the user run `/mcp` and choose Authenticate explicitly on Claude Code, or run `codex mcp login mintlify-admin` on Codex.
- **The tools are there but every call is an auth error**—the grant didn't complete. Redo the browser approval.

## Step 5—offer a first page

Then offer to write something, since that's the fastest way to see what was just connected:

```
Write a one-page overview of this project in Mintlify and send me the editor link
Turn this week's changes into release notes in Mintlify
```

`create_node` with `visibility: "private"`, `parentId: null`, and `data: { type: "page", path, title, content }` writes the page and returns an `editorUrl`. Send the person that link; it opens the page in the Mintlify editor. Tool arguments and the access model are documented at /ai/mintlify-mcp.
