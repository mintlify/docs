Use this to keep docs current or check them on every pull request. Most setup is in the dashboard (https://app.mintlify.com/products/automations), which you cannot click: pick the tool, prepare repo files and CI, and give the user exact dashboard steps.

## Pick the right tool

- Fail a PR on broken builds or links, in any CI, any plan: add `mint validate` and `mint broken-links` to the user's own CI (below).
- Broken internal links and Vale prose linting on GitHub PRs, no CI file: Mintlify CI checks (Pro or Enterprise, GitHub only).
- Recurring or triggered doc updates (code merged, content pushed, schedule, integration event, webhook): an automation (Enterprise).
- "Just keep docs up to date", no prompts or triggers to configure: Autopilot (Pro or Enterprise, on GitHub, GitLab including self-hosted, or Azure Repos).
- One-off or exploratory change: the Mintlify agent in Slack, the web editor, or the dashboard.

## Workflow

1. Run `mint status` to confirm account and subdomain. Ask the plan if a step needs Pro or Enterprise.
2. CI in their repo: add the Examples job yourself.
3. Mintlify CI checks: tell the user to enable them on the dashboard **Site** settings page (https://app.mintlify.com/settings/project/site), choosing `Warning` (never fails) or `Blocking` (fails on errors or suggestions). Needs the Mintlify GitHub App. Optional: commit a `.vale.ini` in the content root (use relative `StylesPath = styles`, no absolute paths or `..`) and `styles/config/vocabularies/Mintlify/accept.txt` / `reject.txt`.
4. Agent guidance: write `.mintlify/AGENTS.md`. A root `AGENTS.md` also works but is served publicly at `/agents.md` unless you add it to `.mintignore`. The Mintlify agent reads only `AGENTS.md`, not `CLAUDE.md`, `.cursorrules` or similar, so copy shared rules in. The editor agent ignores `AGENTS.md`; it uses **AI instructions** in editor settings.
5. Automations: the user creates and manages them on the **Automations** page of the dashboard. Help them choose a name, trigger, and prompt. Prompts: one task, numbered steps, exact paths, done state.
6. Test: user clicks **Test run** / **Run now** and picks a scope (**Since a date**, **Everything**, **Specific pull request**). Not available for Integration or Webhook triggers. Check the **Runs** tab.
7. Autopilot: user opens https://app.mintlify.com/products/autopilot, switches on the toggle, picks **Additional repositories** under GitHub **Configure** (GitLab: **Additional projects**, after connecting projects through GitLab OAuth in Git settings. Azure Repos: **Configure** in the **Azure Repos** row), and uses **Chat to configure** to change reviewers, target branch, or schedule.
8. Slack agent: user clicks **Connect Slack** on the Automations page and installs the `mintlify` app (workspace admin approval may be needed; on Enterprise Grid install to the specific workspace). Test with a DM or `@mintlify` in a channel. The Slack agent also chats with Autopilot: ask about its work or change what it works on. Not available for Bitbucket Cloud projects.

## What each piece does

- The Mintlify agent: researches docs, connected repos and the web, plans, writes, runs CLI checks, then opens a PR or commits to the deploy branch (**Agent review process** in **Slack settings**: **Create a pull request** or **Push to main**; branch protection forces a PR). Name a branch in the prompt to target it. Only reads repos with the Mintlify GitHub App (GitLab: Git Settings); other repos are read-only context. Slack viewers get read-only.
- Web editor agent: **Ask agent** or Cmd/Ctrl+J; edits the current branch.
- Automations: one trigger each. **Content update** (push to docs repo), **Code change** (PR merged in source repos; per-repo path filters and excluded authors, up to 50 repos), **Custom schedule** (presets or 5-field cron), **Integration** (Enterprise, custom only), **Webhook** (custom only, `POST` with `Authorization: Bearer <api-key>`, an organization API key with write access).
- Predefined: Update from code changes (needs a source repo, default twice weekly), Draft changelog, Fill gaps from assistant conversations, Improve docs from user feedback (feedback collection on), Update from support feedback (Intercom, Plain, Pylon, or Zendesk), Translate content (needs a target language, direct merge), Fix broken links, Fix SEO issues, Fix grammar & typos, Enforce your style guide. Custom: your own prompt.
- Output: PRs against the deploy branch, titled with the automation name. No per-automation base branch; to land elsewhere, change the project's deploy branch in Git Settings or use a separate project. Update mode: **Update and merge changes** toggle, off by default. Off opens a PR; on merges directly (GitHub needs the Mintlify GitHub App on the bypass list, mode **Always**, of every ruleset on the deploy branch). Up to 10 context repos.
- Autopilot: decides what to update itself, avoids duplicating active automations, never pushes to the deploy or default branch, assigns the code owner as reviewer (not on Azure Repos). Merges its own PRs only after the user turns on **Auto-merge changes** (shown after 3 merged Autopilot PRs). Default: code changes plus a daily quality check. Can also run on GitHub issue events, set up in a chat.
- Integrations (Enterprise): read-only tools and triggers for automations (Confluence, Jira, Linear, Notion, Stripe, Zendesk, Slack).

## Plans and credits

- Starter has no AI features and cannot buy credits.
- Each Pro plan adds 10,000 credits per month to one organization-wide balance. A project with a credit allocation (Pro or Enterprise) spends it first.
- Automation run that updates docs: 250 credits. Autopilot run it starts itself that opens or updates a PR: 250. Work people ask for: 0. Runs that find nothing or fail: 0. Editor and Slack agent: no credits.
- Scheduled runs batch changes into one 250-credit update; push triggers vary with change volume. Max 500 runs per automation per day. Autopilot pauses itself when credits run out.

## Rules

- Never claim Autopilot, Mintlify CI checks, the Slack app, or an automation is set up: only the user can do those in the dashboard.
- Mintlify CI checks do not check external links; use `mint broken-links --check-external`.
- If the Git provider uses an IP allow list, the user emails support@mintlify.com to route through `54.242.90.151`, then allows that IP.
- GitLab automations need a paid GitLab tier and Maintainer role per project. Mintlify CI checks are GitHub only.

## Examples

```yaml
name: Docs checks
on:
  pull_request:
    paths: ["**/*.mdx", "docs.json"]
jobs:
  docs-checks:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm i -g mint
      - run: mint validate
      - run: mint broken-links --check-anchors
```

Run where `docs.json` lives. In large repos scope with `--files "guides/**/*.mdx"`.

## Verify

```bash
mint validate
mint broken-links --check-anchors --check-redirects --check-snippets
mint dev --no-open
```

Then open a test PR to confirm the CI job runs.
