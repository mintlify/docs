La [page de paramètres](https://app.mintlify.com/settings/deployment/editor) de l'éditeur contrôle l'apparence, le comportement de publication et le comportement de l'agent.

- **Appearance** : Préférences personnelles sur l'aspect et le comportement de l'éditeur. Elles ne s'appliquent qu'à vous.
- **Publishing** : Valeurs par défaut, à l'échelle du deployment, sur la façon dont l'éditeur commit les modifications et ouvre les pull requests. Elles s'appliquent à toutes les personnes qui publient. Seuls les admins peuvent mettre à jour le comportement de publication.
- **Chat** : Instructions persistantes pour l'agent d'IA de l'éditeur.
- **Danger zone** : Actions irréversibles.

<div id="appearance">

## Appearance

</div>

Les paramètres d'apparence sont des préférences personnelles. Ils ne modifient l'éditeur que pour vous et n'affectent ni vos coéquipiers ni votre site publié. Tous les paramètres d'apparence sont désactivés par défaut.

- **Fit editor to full width** : Étend la zone d'édition d'un bord à l'autre au lieu de la colonne de 768px par défaut.
- **Show breadcrumbs** : Affiche l'emplacement de la page dans la navigation du site au-dessus de la zone d'édition.
- **Open live preview in new tab** : Lors de la prévisualisation, ouvre la page rendue dans un nouvel onglet du navigateur.

<div id="pr-merge-method">

## Méthode de fusion des PR

</div>

Choisissez comment l'éditeur fusionne les pull requests lorsque vous cliquez sur **Merge and publish** :

- **Merge** : Crée un commit de fusion qui conserve tout l'historique de la branch. C'est l'option par défaut.
- **Squash** : Combine tous les commits de la branch en un seul commit sur votre deployment branch.
- **Rebase** : Rejoue chaque commit de la branch sur votre deployment branch sans commit de fusion.

<Tip>
  Faites correspondre votre méthode de fusion aux règles de protection de branch de votre fournisseur Git. Si votre deployment branch n'autorise que les squash merges, choisissez **Squash** pour éviter les fusions en échec depuis l'éditeur.
</Tip>

<div id="auto-publish">

## Publication automatique

</div>

La publication automatique commit automatiquement les modifications sur votre deployment branch, peu après que vous arrêtez d'écrire. Si vous activez ce paramètre, l'éditeur masque les branches et l'étape de publication pour toutes les personnes de votre site. La publication automatique est désactivée par défaut.

<Warning>
  Avec la publication automatique activée, il n'y a ni état en attente ni possibilité de relecture. Chaque modification atteint votre site publié peu après que vous arrêtez d'écrire.
</Warning>

<div id="create-draft-pull-requests-by-default">

## Créer les pull requests en brouillon par défaut

</div>

Lorsque ce paramètre est activé, les pull requests créées depuis l'éditeur s'ouvrent en brouillon, y compris la pull request qui s'ouvre après le premier commit sur une nouvelle branch. Les auteurs cliquent sur **Request review** pour les marquer comme prêtes lorsqu'ils ont terminé leurs modifications. Ce paramètre est activé par défaut.

Si vous voulez que les pull requests de l'éditeur s'ouvrent immédiatement prêtes à être relues, désactivez les pull requests en brouillon.

<div id="granular-publishing">

## Publication granulaire

</div>

La publication granulaire contrôle quelles modifications en attente le menu **Publish** affiche sur votre deployment branch.

- **Désactivée (par défaut)** : Le menu **Publish** n'affiche et ne publie que vos propres modifications. Les modifications effectuées uniquement par vos collègues sont masquées.
- **Activée** : Le menu **Publish** affiche toutes les modifications en attente, réparties entre **Your changes** et **Modified by others**, avec une case à cocher sur chaque modification pour vous permettre de choisir ce qui sera publié.

Ce paramètre ne prend effet que lorsque vous travaillez sur votre deployment branch et que cette branch n'a pas de protections de branch. Consultez [Publier des modifications spécifiques](/fr/editor/publish#publish-specific-changes) pour plus d'informations.

<div id="pr-instructions">

## Instructions de PR

</div>

Les instructions de PR guident l'IA lorsqu'elle génère le titre et la description d'une pull request. Elles s'appliquent chaque fois que l'éditeur génère une description de pull request en votre nom.

Utilisez les instructions de PR pour normaliser ce que voient les relecteurs, par exemple :

- Des sections obligatoires comme **Summary** et **Changes**.
- Un modèle de description qui renvoie vers un système de suivi.
- Des exigences de ton ou de longueur pour les titres.

Exemple :

```text
Title: imperative mood, under 70 characters, no trailing period.
Description: include a "## Summary" section (one sentence) and a
"## Changes" section as a bulleted list. Link any referenced page
using its relative path.
```

Les instructions sont limitées à 20 000 caractères.

<div id="ai-instructions">

## Instructions d'IA

</div>

Les instructions d'IA sont des consignes persistantes que l'éditeur transmet à l'IA en même temps que votre demande. Utilisez-les pour consigner les règles de style et de ton que vous ne voulez pas répéter à chaque fois, comme la voix, la terminologie ou les conventions de mise en forme.

Vos instructions s'appliquent :

- Aux prompts **Ask AI**, que vous ouvrez en appuyant sur <kbd>Space</kbd> sur une ligne vide.
- Aux sessions de l'agent lancées depuis l'éditeur.

Chaque membre de l'équipe gère ses propres instructions, liées à son compte utilisateur. Les instructions sont limitées à 20 000 caractères.

Ajoutez des instructions d'IA lorsque vous constatez que vous répétez les mêmes consignes dans vos prompts, par exemple :

- Imposer la deuxième personne ou des titres en casse de phrase.
- Privilégier des noms de produit ou une terminologie précis.
- Interdire le langage marketing ou les formules de remplissage.
- Exiger certains composants, comme toujours utiliser `<Note>` pour les encadrés.

Gardez des instructions courtes et précises. L'IA les suit à chaque demande, donc des règles vagues ou contradictoires dégradent les résultats.

Exemple :

```text
- Use second person ("you") and active voice.
- Use sentence case for all headings.
- Refer to the product as "Acme"—never "Acme Inc." or "the platform".
- Wrap notes and warnings in <Note> or <Warning> components.
- Do not add introductory filler like "In this guide" or "Let's explore".
```

Laissez le champ vide pour supprimer vos instructions.

<div id="reset-editor">

## Réinitialiser l'éditeur

</div>

**Reset editor** force l'éditeur à abandonner son état local et à se synchroniser avec votre dépôt Git. Après confirmation, l'éditeur se recharge. Seuls les admins peuvent réinitialiser l'éditeur. Réinitialisez l'éditeur s'il reste désynchronisé par rapport à votre dépôt, par exemple si l'arborescence de fichiers est vide ou affiche des erreurs comme `Unable to find docs.json`. Cela peut se produire alors même que le fichier existe sur votre deployment branch et que votre site se compile normalement.

<Warning>
  Si vous réinitialisez l'éditeur, vous perdez toutes les modifications non publiées que vous n'avez pas commitées dans Git. Si vous avez des modifications en attente que vous voulez conserver, publiez-les d'abord.
</Warning>
