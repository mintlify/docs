Un grafo de conocimiento del código es un proyecto de Mintlify que describe tu código: qué hace cada repositorio, qué expone y cómo dependen los repositorios entre sí. Los agentes lo consultan mediante MCP antes de modificar el código.

No necesitas documentación existente ni una migración. La configuración consta de tres pasos:

1. [Genera el grafo de conocimiento inicial](#step-1-generate-the-initial-knowledge-graph) con el agente de Mintlify o con tu propio agente de programación.
2. [Configura automatizaciones](#step-2-keep-the-knowledge-graph-current) para mantenerlo actualizado.
3. [Usa el grafo de conocimiento mediante MCP](#step-3-use-the-knowledge-graph-through-mcp).

<Note>

</Note>

<div id="prerequisites">
  ## Requisitos previos
</div>

- Un proyecto de Mintlify conectado a un repositorio de Git. Este repositorio central contiene el grafo de conocimiento y puede empezar vacío. Consulta la [Guía rápida](/es/quickstart).
- La [GitHub App de Mintlify](/es/deploy/github) instalada en el repositorio central y en cada repositorio de origen que quieras documentar.
- Un [plan Enterprise](https://mintlify.com/pricing?ref=knowledge-graph) para las [automatizaciones personalizadas](/es/automations/create).
- [Autenticación](/es/deploy/authentication-setup) en el proyecto, para que solo tu equipo pueda leer el grafo de conocimiento y conectarse a su servidor MCP. Sin autenticación, cualquiera puede leer las páginas que describen tu código interno.
- El [agente de Mintlify](/es/agent/index) o un agente de programación como [Claude Code](/es/guides/claude-code), [Codex](/es/guides/codex) o [Cursor](/es/guides/cursor).

<div id="plan-the-structure">
  ## Planifica la estructura
</div>

Coloca todos los repositorios en un único proyecto central, para que los agentes consulten un solo servidor MCP y las páginas puedan enlazarse entre repositorios. Asigna a cada repositorio su propio grupo, además de una sección de descripción general.

```json docs.json
{
  "navigation": {
    "groups": [
      {
        "group": "Overview",
        "pages": ["index", "architecture", "glossary"]
      },
      {
        "group": "Web app",
        "pages": ["repos/web-app/index", "repos/web-app/local-development", "repos/web-app/routing"]
      },
      {
        "group": "API service",
        "pages": ["repos/api-service/index", "repos/api-service/endpoints", "repos/api-service/data-model"]
      },
      {
        "group": "API gateway",
        "pages": ["repos/api-gateway/index", "repos/api-gateway/auth"]
      }
    ]
  }
}
```

La sección de cada repositorio debe cubrir lo que un agente necesita saber antes de modificar el código:

- Qué hace el repositorio y quién es responsable de él
- Los endpoints o eventos que expone
- A qué llama y qué lo llama
- Sus modelos de datos principales
- Cómo ejecutarlo y probarlo

Empieza con unos pocos repositorios representativos, como un frontend, un backend y un servicio compartido, antes de añadir el resto.

<div id="step-1-generate-the-initial-knowledge-graph">
  ## Paso 1: Genera el grafo de conocimiento inicial
</div>

Haz que un agente lea tu código fuente y escriba las primeras páginas en el repositorio central. Usa el agente de Mintlify, o clona los repositorios y ejecuta tu propio agente de programación.

<Tabs>
  <Tab title="Agente de Mintlify">
    El [agente de Mintlify](/es/agent/index) lee cualquier repositorio que tenga instalada la GitHub App de Mintlify, así que no necesitas clonar nada.

    <Steps>
      <Step title="Genera la documentación de un repositorio">
        Abre el agente en tu [dashboard](https://app.mintlify.com) o en [Slack](/es/agent/slack) e indica el repositorio de origen, la carpeta de destino y las páginas que debe escribir.

        ```text Example prompt
        Read the source code in the your-org/api-service repository and write
        documentation for it in repos/api-service/.

        Create these pages:
        - index.mdx: what the service does, who owns it, and how it fits into the
          rest of the system
        - endpoints.mdx: every HTTP endpoint with method, path, parameters, and
          response shape, based on the route definitions
        - data-model.mdx: the main models and database tables
        - local-development.mdx: how to install, run, and test the service

        For each page, list the other repositories this service calls or is called
        by, and link to their pages under repos/.

        Only document what you can confirm from the code. If something is unclear,
        leave a TODO comment instead of guessing.

        Add the new pages to docs.json in a group named "API service".
        ```

        El agente abre una pull request en el repositorio central. Revísala y corrige cualquier error que haya cometido el agente.
      </Step>
      <Step title="Repite el proceso para cada repositorio">
        Repite el proceso con tus otros repositorios y, después, pide al agente las páginas de descripción general.

        ```text Example prompt
        Read every page under repos/ and write architecture.mdx. Describe how the
        repositories depend on each other, which services call which, and how a
        request moves through the system. Link to the repository pages for details.
        ```
      </Step>
      <Step title="Fusiona las pull requests">
        Cuando se fusionan las pull requests, Mintlify despliega el grafo de conocimiento y lo indexa para la búsqueda y MCP.
      </Step>
    </Steps>
  </Tab>
  <Tab title="Clonar y hacer push">
    Ejecuta Claude Code, Codex o Cursor sobre clones locales y, después, haz push de las páginas al repositorio central.

    <Steps>
      <Step title="Configura tu agente de programación">
        Clona el repositorio central y los repositorios de origen en un mismo directorio principal.

        ```bash
        mkdir knowledge-graph && cd knowledge-graph
        git clone https://github.com/your-org/docs-hub.git
        git clone https://github.com/your-org/web-app.git
        git clone https://github.com/your-org/api-service.git
        git clone https://github.com/your-org/api-gateway.git
        ```

        Ejecuta [`mint agent setup`](/es/cli/commands#mint-agent-setup) con `--global` para instalar la skill de Mintlify y conectar el [servidor MCP de administración](/es/ai/mintlify-mcp) para tu cuenta de usuario. Sin `--global`, el comando configura solo el repositorio central, y un agente que inicies en el directorio principal no carga esa configuración.

        ```bash
        mint agent setup --global
        ```
      </Step>
      <Step title="Genera la documentación de un repositorio">
        Inicia tu agente en el directorio principal e indica el repositorio de origen, la carpeta de destino y las páginas que debe escribir.

        ```text Example prompt
        Read the source code in ../api-service and write documentation for it in
        docs-hub/repos/api-service/.

        Create these pages:
        - index.mdx: what the service does, who owns it, and how it fits into the
          rest of the system
        - endpoints.mdx: every HTTP endpoint with method, path, parameters, and
          response shape, based on the route definitions
        - data-model.mdx: the main models and database tables
        - local-development.mdx: how to install, run, and test the service

        For each page, list the other repositories this service calls or is called
        by, and link to their pages under docs-hub/repos/.

        Only document what you can confirm from the code. If something is unclear,
        leave a TODO comment instead of guessing.

        Add the new pages to docs-hub/docs.json in a group named "API service".
        ```

        Revisa el resultado, corrige cualquier error que haya cometido el agente y ejecuta `mint dev` desde el repositorio central para previsualizar las páginas.
      </Step>
      <Step title="Repite el proceso para cada repositorio">
        Repite el proceso con tus otros repositorios y, después, pide al agente las páginas de descripción general.

        ```text Example prompt
        Read every page under docs-hub/repos/ and write docs-hub/architecture.mdx.
        Describe how the repositories depend on each other, which services call
        which, and how a request moves through the system. Link to the repository
        pages for details.
        ```
      </Step>
      <Step title="Haz push al repositorio central">
        Haz commit de las páginas, haz push al repositorio central y abre una pull request. Cuando se fusione, Mintlify desplegará el grafo de conocimiento y lo indexará para la búsqueda y MCP.

        ```bash
        git checkout -b initial-knowledge-graph
        git add repos architecture.mdx docs.json
        git commit -m "Add initial knowledge graph"
        git push -u origin initial-knowledge-graph
        ```
      </Step>
    </Steps>
  </Tab>
</Tabs>

<Tip>
  Guarda los prompts que te hayan funcionado como una [skill personalizada](/es/ai/skillmd#custom-skill-files) o en un archivo `AGENTS.md` en el repositorio central. Así, quien añada un repositorio nuevo más adelante obtendrá la misma estructura de páginas.
</Tip>

<div id="step-2-keep-the-knowledge-graph-current">
  ## Paso 2: Mantén actualizado el grafo de conocimiento
</div>

Crea una [automatización personalizada](/es/automations/create) con un activador de cambio de código para que el agente actualice el repositorio central cada vez que se fusione una pull request en un repositorio de origen.

<Steps>
  <Step title="Crea la automatización">
    1. Abre la configuración de [Automatizaciones](https://app.mintlify.com/settings/project/automations).
    2. Haz clic en **New automation**.
    3. Selecciona el activador **Code change**.
    4. Haz clic en **Add repo** para cada repositorio de origen que documentaste en el paso 1. Una automatización puede escuchar hasta 50 repositorios.
  </Step>
  <Step title="Filtra el activador">
    En la tarjeta de cada repositorio, haz clic en **Show advanced options**. Configura **Listening to changes in** con rutas de código fuente como `src/**` y añade las cuentas de bots a **Exclude author**. Consulta [Filtrar activadores de cambio de código](/es/automations/manage#filter-code-change-triggers).
  </Step>
  <Step title="Escribe las instrucciones">
    Indica al agente cómo se corresponden los repositorios con las páginas del repositorio central y qué debe cambiar.

    ```text Example instructions
    1. Read the merged pull request diff from the trigger repository.
    2. Find the matching folder under /repos/ in this project. The folder name
       matches the repository name.
    3. Identify changes to endpoints, events, data models, dependencies on
       other repositories, or setup steps.
    4. Update the affected pages in that folder. If the change affects how
       repositories depend on each other, also update /architecture.mdx.
    5. If the pull request doesn't change anything the documentation covers,
       make no changes.
    6. Open a pull request that lists the pages you changed and links to the
       source pull request.
    ```

  </Step>
  <Step title="Elige un modo de actualización">
    Al principio, deja **Update and merge changes** desactivado. Así, el agente abre una pull request y asigna como revisores a los autores del cambio de origen. Cuando las pull requests del agente dejen de necesitar correcciones, activa **Update and merge changes**. Si tu rama de despliegue tiene protección de ramas, consulta [Configurar la fusión automática](/es/guides/configure-automerge).
  </Step>
  <Step title="Prueba la automatización">
    Guárdala y [ejecútala manualmente](/es/automations/manage#run-an-automation-manually); después, revisa el [historial de ejecuciones](/es/automations/manage#view-run-history) y ajusta las instrucciones.
  </Step>
</Steps>

Este simulador usa una automatización que escucha `src/**` en los tres repositorios de ejemplo y excluye a `dependabot[bot]`.

<KgTriggerSimulator />

Para añadir un repositorio más adelante, genera sus páginas como en el paso 1 y, después, añádelo al activador.

Cada ejecución que actualiza el repositorio central consume créditos, y las ejecuciones que no cambian nada son gratuitas. En repositorios con mucha actividad, un activador programado agrupa muchas fusiones en una sola ejecución. Consulta [Controlar el uso de créditos](/es/guides/use-automations#control-credit-usage).

<div id="step-3-use-the-knowledge-graph-through-mcp">
  ## Paso 3: Usa el grafo de conocimiento mediante MCP
</div>

Cada proyecto tiene un [servidor MCP de búsqueda](/es/ai/model-context-protocol) alojado. Como el grafo de conocimiento requiere autenticación, conecta tus agentes a la ruta `/authed/mcp` de la URL de tu sitio. La primera vez que un agente se conecta, inicias sesión con las mismas credenciales que usas para el sitio, y el agente solo lee las páginas a las que pueden acceder tus [grupos de usuarios](/es/deploy/authentication-setup). Consulta [Habilitar el MCP autenticado](/es/ai/model-context-protocol#enable-authenticated-mcp).

<Tabs>
  <Tab title="Claude Code">
    ```bash
    claude mcp add --transport http knowledge-graph https://docs.example.com/authed/mcp
    ```
  </Tab>
  <Tab title="Codex">
    ```bash
    codex mcp add knowledge-graph --url https://docs.example.com/authed/mcp
    ```
  </Tab>
  <Tab title="Cursor">
    Añade el servidor a `.cursor/mcp.json` en tu proyecto, o a `~/.cursor/mcp.json` para todos los proyectos.

    ```json .cursor/mcp.json
    {
      "mcpServers": {
        "knowledge-graph": {
          "url": "https://docs.example.com/authed/mcp"
        }
      }
    }
    ```
  </Tab>
</Tabs>

Consulta [Usar tu servidor MCP](/es/ai/model-context-protocol#use-your-mcp-server) para otros clientes.

Para comprobar la conexión, pregunta a tu agente cómo ejecutar en local uno de tus repositorios. Confirma que el agente busca en el servidor `knowledge-graph` y responde a partir de sus páginas.

Para que los agentes lo consulten sin que se lo pidas, añade una línea al archivo `CLAUDE.md`, `AGENTS.md` o de reglas de Cursor en cada repositorio de origen.

```markdown AGENTS.md
Before changing code that calls another service or repository, search the
knowledge-graph MCP server for that service. Use its documented endpoints,
data models, and conventions instead of guessing.
```

export const KgCreditEstimator = () => {
  const schedules = [
    { id: "daily", label: "Diaria", runs: 7 },
    { id: "twice", label: "Dos veces por semana", runs: 2 },
    { id: "weekly", label: "Semanal", runs: 1 },
  ];
  const [merges, setMerges] = useState(40);
  const [scheduleId, setScheduleId] = useState("daily");
  const schedule = schedules.find((s) => s.id === scheduleId);
  const perRun = 250;
  const pushRuns = merges;
  const scheduledRuns = Math.min(merges, schedule.runs);
  const push = pushRuns * perRun;
  const scheduled = scheduledRuns * perRun;
  const max = Math.max(push, scheduled, perRun);
  const fmt = (n) => n.toLocaleString("en-US");
  const bars = [
    { label: "Activador de cambio de código", runs: pushRuns, credits: push, note: "Una ejecución por cada pull request fusionada" },
    { label: `Programación ${schedule.label.toLowerCase()}`, runs: scheduledRuns, credits: scheduled, note: `Hasta ${schedule.runs} ${schedule.runs === 1 ? "ejecución" : "ejecuciones"} por semana, cada una agrupando todas las fusiones desde la ejecución anterior` },
  ];
  return (
    <KgFrame title="Estimación semanal de créditos" caption="250 créditos por cada ejecución que actualiza la documentación">
      <label style={{ display: "grid", gap: 6 }}>
        <span style={{ display: "flex", justifyContent: "space-between", gap: 8, fontSize: 13 }}>
          <span style={{ fontWeight: 600 }}>Pull requests fusionadas por semana que cambian código documentado</span>
          <span style={{ fontVariantNumeric: "tabular-nums" }}>{merges}</span>
        </span>
        <input type="range" min={0} max={150} step={1} value={merges} onChange={(e) => setMerges(Number(e.target.value))} style={{ width: "100%", accentColor: KgTheme.accent }} />
      </label>
      <div style={{ display: "flex", flexWrap: "wrap", alignItems: "center", gap: 8 }}>
        <span style={{ fontSize: 12, opacity: 0.65 }}>Programación para comparar</span>
        {schedules.map((s) => <KgButton key={s.id} pressed={s.id === scheduleId} onClick={() => setScheduleId(s.id)}>{s.label}</KgButton>)}
      </div>
      <div style={{ display: "grid", gap: 12 }}>
        {bars.map((b) => (
          <div key={b.label} style={{ display: "grid", gap: 4 }}>
            <div style={{ display: "flex", flexWrap: "wrap", justifyContent: "space-between", gap: 8, fontSize: 13 }}>
              <span style={{ fontWeight: 600 }}>{b.label}</span>
              <span style={{ fontVariantNumeric: "tabular-nums" }}>{fmt(b.credits)} créditos · {b.runs} {b.runs === 1 ? "ejecución" : "ejecuciones"}</span>
            </div>
            <div style={{ height: 12, borderRadius: 6, background: KgTheme.surface, overflow: "hidden" }}>
              <div style={{ height: "100%", width: `${(b.credits / max) * 100}%`, minWidth: b.credits ? 4 : 0, borderRadius: 6, background: KgTheme.accent, transition: "width .3s ease" }} />
            </div>
            <div style={{ fontSize: 12, opacity: 0.65 }}>{b.note}</div>
          </div>
        ))}
      </div>
      <div style={{ fontSize: 13, padding: 10, borderRadius: 8, background: KgTheme.surface }}>
        {merges === 0 ? "Sin fusiones, ninguna opción se ejecuta, así que ninguna cuesta nada." : push === scheduled ? "Ambas opciones cuestan lo mismo con este volumen. El activador de cambio de código actualiza la documentación antes." : `La programación ${schedule.label.toLowerCase()} usa ${fmt(push - scheduled)} créditos menos por semana. La contrapartida es que la documentación puede ir por detrás del código hasta ${schedule.runs === 7 ? "un día" : schedule.runs === 2 ? "media semana" : "una semana"}.`}
      </div>
    </KgFrame>
  );
};
