在更改进入你的线上站点之前先进行预览，请同事批准这些更改，并在编辑器中发布或合并它们。

<div id="live-preview">

## 实时预览

</div>

实时预览会在你编辑时渲染站点，无需构建步骤。打开站点页面后，点击顶部栏中的 <Icon icon="play" /> **Preview**。预览会全屏打开。点击 **Refresh preview** 可重新加载，或点击 **Close preview** 返回编辑器。若要改为在新的浏览器标签页中打开预览，请开启 [Open live preview in new tab](/zh/editor/settings#appearance)。

若要编辑站点设置并查看其对内容的影响，请点击预览工具栏中的 **Site settings**，然后选择一个配置分区。

若要在预览旁边打开[智能体](/zh/editor/agent)，请点击预览工具栏中的 **Ask agent**。只有 editors 和 admins 才能在实时预览中使用智能体。

<Note>
  使用独立[个性化](/zh/create/personalization)功能但未启用认证的站点无法使用实时预览。
</Note>

<div id="preview-deployments">

## 预览部署

</div>

<Info>
  预览部署需要 [Pro 或 Enterprise 方案](https://mintlify.com/pricing?ref=preview-deployments)。限制预览的访问权限需要 [Enterprise 方案](https://mintlify.com/pricing?ref=preview-deployments)。
</Info>

当你的 feature branch 存在 pull request 时，Mintlify 会构建一个预览部署：一个临时 URL，你的更改会在其中以发布后完全一致的方式呈现。每当编辑器向该分支提交新更改时，预览都会重新构建。该 URL 由你项目的子域名和分支名称组合而成：`<subdomain>-<branch-name>.mintlify.site`。你可以在 Mintlify 机器人的 pull request 评论中找到确切的 URL。

预览 URL 默认可公开访问。你可以在仪表板的[站点](https://app.mintlify.com/settings/project/site)页面的 **Previews** 分区中启用预览认证，将访问权限限制为你的 Mintlify 组织成员。更多信息请参阅[限制预览部署的访问权限](/zh/deploy/preview-deployments#restrict-access-to-preview-deployments)。

<div id="which-preview-to-use">

## 该使用哪种预览

</div>

| 功能 | 实时预览 | 预览部署 |
|---|---|---|
| **速度** | 即时 | 需要构建 |
| **访问方式** | 在编辑器内 | 可共享的 URL |
| **适用场景** | 编辑时审阅更改 | 与团队共享以供审阅 |
| **可用时长** | 编辑器打开期间 | 只要该分支存在 |

<div id="share-an-editor-link">

## 共享编辑器链接

</div>

若要把同事引导到分支上的某个特定页面，请点击页面右上角的 <Icon icon="ellipsis" /> **More options**，然后点击 **Copy link**。任何有权访问你 Mintlify 组织的人都可以在自己的编辑器会话中打开该链接。

<div id="require-review-before-publishing">

## 发布前要求审阅

</div>

<Info>
  Require review before publishing 目前处于 beta 阶段，可能会发生变化。要在发布前要求审阅，你必须使用 [Enterprise 方案](https://mintlify.com/pricing?ref=review)，并且项目的仓库必须托管在 GitHub 上。
</Info>

如果 admin 开启了 [Require review before publishing](/zh/editor/settings#require-review-before-publishing)，deployment branch 以及你在编辑器中创建的 branch 上的更改需要先获得同事批准，admin 或 publisher 才能发布。admins 可以不经审阅直接发布自己的更改，除非你的 deployment branch 启用了分支保护。

在 branch 上，审阅者会在编辑器中一次性批准该 branch 上的所有更改。请参阅[审阅 branch 上的更改](#review-changes-on-a-branch)。

每个[角色](/zh/dashboard/roles)拥有不同的发布权限。

| 角色 | 请求审阅 | 批准更改 | 发布已批准的更改 | 不经审阅直接发布 |
| --- | :---: | :---: | :---: | :---: |
| Owner 和 admin | <Icon icon="check" color="#16a34a" /> 是 | <Icon icon="check" color="#16a34a" /> 是 | <Icon icon="check" color="#16a34a" /> 是 | <Icon icon="check" color="#16a34a" /> 是 |
| Publisher | <Icon icon="check" color="#16a34a" /> 是 | <Icon icon="check" color="#16a34a" /> 是 | <Icon icon="check" color="#16a34a" /> 是 | <Icon icon="x" color="#dc2626" /> 否 |
| Editor（组织有 publisher 角色时） | <Icon icon="check" color="#16a34a" /> 是 | <Icon icon="x" color="#dc2626" /> 否 | <Icon icon="x" color="#dc2626" /> 否 | <Icon icon="x" color="#dc2626" /> 否 |
| Editor（组织没有 publisher 角色时） | <Icon icon="check" color="#16a34a" /> 是 | <Icon icon="check" color="#16a34a" /> 是 | <Icon icon="x" color="#dc2626" /> 否 | <Icon icon="x" color="#dc2626" /> 否 |
| Commenter | <Icon icon="x" color="#dc2626" /> 否 | <Icon icon="x" color="#dc2626" /> 否 | <Icon icon="x" color="#dc2626" /> 否 | <Icon icon="x" color="#dc2626" /> 否 |
| Viewer | <Icon icon="x" color="#dc2626" /> 否 | <Icon icon="x" color="#dc2626" /> 否 | <Icon icon="x" color="#dc2626" /> 否 | <Icon icon="x" color="#dc2626" /> 否 |

<div id="request-a-review">

### 请求审阅

</div>

1. 在 deployment branch 或某个 branch 上进行更改。
1. 点击顶部栏中的 **Request review**。当你的更改需要审阅时，此按钮会替代 **Publish**。
1. 在 **Request review** 部分，点击 **Choose reviewers** 并选择人员或群组。你只能选择有权批准更改的成员。
1. 点击 **Request**。

该请求包含你更改过且尚未处于审阅中的所有页面。每位审阅者都会收到一封电子邮件和一条[收件箱](/zh/dashboard/inbox)项目。

不属于某个页面的更改（例如导航、站点设置以及已删除的非页面文件）会作为一个 **Site changes** 项目加入请求。审阅者批准 **Site changes** 的方式与批准页面相同。每个上传的文件都是请求中的一个单独项目。

当页面处于未完成的审阅请求中时，侧边栏会在其旁边显示 **In review**。审阅者批准该页面后，侧边栏会显示 **Approved**。

在未受保护的 deployment branch 上，admins 可以不经审阅直接发布，但也可以从 **Publish** 菜单请求审阅。

<div id="review-and-approve-changes">

### 审阅并批准更改

</div>

1. 从收件箱或电子邮件中打开审阅请求，或打开有人请你审阅的页面。
1. 阅读更改。审阅中的页面会以差异视图打开，包括对页面标题和描述的更改。在源代码模式下，你会看到文本差异。如果要留下评论或建议而不是批准，请使用[评论和建议工具](/zh/editor/collaborate)。评论和建议既不会批准审阅，也不会阻止审阅。
1. 点击页面顶部横幅中的 **Approve**。你的批准适用于该请求中的所有页面。

你无法批准自己的审阅请求。

要查看不带高亮更改的页面，请点击工具栏中的 **Hide changes**。点击 **Show changes** 可重新显示更改。你的选择会沿用到审阅中的其他页面和 **Site settings**。

如果审阅请求只包含站点更改和上传的文件，其横幅会显示在 **Site settings** 和每个上传的文件上，而不是显示在页面上。该请求的审阅链接和收件箱项目会打开 **Site settings**。

要审阅站点更改，请在 **Site settings** 中打开任意已更改的部分，然后点击顶部栏中的 **Show changes**。每个字段（例如站点名称、主色或 logo）都会显示更改前后的值，并与你的更改所发布到的 branch 进行比较。显示更改时无法编辑字段。点击 **Hide changes** 即可返回编辑。

在 **Navigation** 部分中，树会用绿色标记新增的项目，用红色标记删除的项目，并为更改的项目显示旧值和新值。包含更改的分组会显示一个圆点，展开即可查看更改内容。

要审阅 `docs.json` 的更改，请在 source 模式下打开它，然后点击顶部栏中的 **Show changes** 查看只读的文本 diff。**Show changes** 仅在审阅期间且 `docs.json` 有更改时才会出现。

<div id="publish-approved-changes">

### 发布已批准的更改

</div>

当有人批准审阅请求后，请求者会收到一条收件箱项目，通知其请求已获批准。admins 和 publishers 可以发布已批准的更改。

1. 打开已批准请求中的某个页面。
1. 点击顶部栏中的 **Publish**。**Publish** 菜单会列出请求者的更改。
1. 点击 **Publish** 加请求者姓名的按钮，例如 **Publish Ronan's changes**，然后点击 **Publish** 确认。

只有已批准的项目才会发布。如果审阅者批准了请求中的 **Site changes** 项目，请求者的导航和站点设置更改会与已批准的页面一起发布。

如果另一个未完成的审阅请求包含对导航或配置的未批准更改，这些更改会保持未发布状态，直到有人批准或撤回另一个请求。

<div id="edit-a-page-after-approval">

### 批准后编辑页面

</div>

批准只适用于审阅者所批准的页面版本。如果你编辑、重命名或移动已批准的页面，必须在发布前重新请求审阅。

同一请求中其他已批准的页面会保留其批准。只有你更改过的页面需要重新审阅，横幅中的 **Request review again** 会请审阅者仅审阅这些页面。

这同样适用于 **Site changes** 和上传的文件。如果你更改了已批准的站点更改或替换了已批准的文件，批准将不再适用。横幅会显示 **Request review again**，以便你请审阅者批准新版本。

<div id="withdraw-a-review-request">

### 撤回审阅请求

</div>

要在有人批准之前撤回你的审阅请求，请打开该请求中的某个页面，然后点击横幅中的 **Withdraw**。对于只包含站点更改和上传文件的请求，请使用 **Site settings** 中的横幅。

要移除某位审阅者，请打开 **Publish** 菜单，然后点击该审阅者姓名旁的 **Withdraw**。如果你移除了所有审阅者，该请求会关闭。

如果你丢弃了请求中的所有更改，该请求会关闭。

<div id="review-changes-on-a-branch">

### 审阅 branch 上的更改

</div>

当你的项目要求发布前审阅时，你在编辑器中创建的 branch 会使用与 deployment branch 相同的审阅流程。你在编辑器中请求审阅和批准更改，不会看到该 branch 的 pull request。发布时，编辑器会将该 branch 合并到你的 deployment branch。

branch 上的审阅涵盖整个 branch。branch 的每个页面都显示同一个横幅，例如 **This branch is under review by** 加审阅者姓名，之后显示 **This branch is approved.** 点击横幅中的 **Approve** 即可一步批准整个 branch。

- branch 会一次性整体发布。只有在审阅者批准了 branch 上的所有更改后，admin 或 publisher 才能发布它，然后点击 **Publish approved changes**。
- 对导航、站点设置以及其他非页面文件的更改会作为 **Site changes** 加入审阅。在审阅者批准这些更改之前，只有 admin 可以发布该 branch。
- admins 可以随时发布 branch。
- 任何有权批准更改的人都可以批准 branch，但创建该 branch 的人和请求审阅的人除外。
- 如果你移动或重新排序已批准的页面，只有该页面需要重新审阅。添加页面或更改导航不会影响其他页面的批准。
- 如果你在批准后编辑了 branch，或有人在 Git 中向其推送了更改，横幅会显示 **You edited this branch after it was approved** 或 **This branch changed in git after it was approved**。点击 **Request review again** 请审阅者重新审阅。
- 你在 branch 上删除的页面也属于审阅的一部分。它们显示为 **Removed**，审阅者会像批准其他页面一样批准它们。审阅横幅中已删除页面的链接会在新标签页中打开该页面在 deployment branch 上的版本。
- 如果 branch 不再更改某个已请求审阅的页面，该页面会离开审阅请求。
- 同事在 GitHub 中对该 branch 的 pull request 留下的审阅会显示在审阅请求和[收件箱](/zh/dashboard/inbox)中，仅供参考。它们不算作编辑器中的批准。
- 如果其他人已发布了对页面同一部分的更改，该 branch 就会产生冲突，在你解决冲突之前无法发布。参见[解决 branch 上的冲突](#resolve-conflicts-on-a-branch)。

在 [sub-branch](/zh/editor/publish#sub-branches) 上，发布菜单仍会显示 **Publish to** 你的 deployment branch 以及 **Merge into** 父 branch。

<div id="resolve-conflicts-on-a-branch">

### 解决 branch 上的冲突

</div>

如果有人发布了对页面某一部分的更改，而你的 branch 也更改了同一部分，发布菜单会显示 **Can't publish these changes** 并禁用 **Publish**。提示中会列出存在冲突的页面。点击某个页面即可查看别人发布的内容。

存在冲突的页面会在侧边栏中显示 **Conflict**，并显示一个带有 **Resolve conflicts** 的横幅。要解决某个页面的冲突：

1. 点击横幅中的 **Resolve conflicts**，或在发布菜单中点击该页面。
1. 对每个编号的冲突，选择 **Keep yours**、**Use published** 或 **Keep both**。在源代码模式下，你也可以直接编辑结果。无法显示可视化差异的页面会以源代码模式打开。
1. 点击 **Save**。要撤销你在该页面上的选择，点击 **Reset**。

保存最后一个存在冲突的页面后，编辑器会用你的选择和其他已发布的更改更新你的 branch，**Request review** 也会重新出现。

在保存之前，你的选择会保留在当前浏览器中，即使重新加载页面也不会丢失。在其他浏览器或设备上，你需要重新开始。

有些文件无法在页面内解决，例如已重命名或已删除的页面，以及非页面文件。对于这些文件，发布菜单会为每个文件提供选项，例如保留你的版本、使用已发布的版本或删除该文件。做出最后一个选择后，在 **Update this branch?** 对话框中点击 **Update branch**。

如果冲突出现在 `docs.json` 中，请向 admin 寻求帮助。

如果在你解决冲突期间 branch 或已发布的版本发生了变化，编辑器会要求你重新选择。你解决过冲突的页面需要重新审阅，即使你保留了自己的版本。其他页面的批准保持不变。

<div id="review-with-a-protected-deployment-branch">

### 在受保护的 deployment branch 上审阅

</div>

如果你的 deployment branch 启用了分支保护，只要仓库托管在 GitHub.com 上，你仍然可以要求发布前审阅。deployment branch 受保护的 GitHub Enterprise Server 仓库无法使用该设置。

1. 在 deployment branch 上，点击 **Create branch** 将你的更改移动到新的 branch。
1. 点击 **Request review** 并选择审阅者。Mintlify 会打开该 branch 的 pull request，或将其草稿 pull request 标记为可供审阅，然后发送审阅请求。
1. 审阅者从收件箱中打开请求，并在编辑器中点击 **Approve**。
1. 批准后，admin 或 publisher 点击 **Publish approved changes**。

如果审阅者已[连接其 GitHub 账号](/zh/dashboard/profile#connect-github)，在编辑器中批准时也会针对其审阅的 commit 在 GitHub 中批准该 pull request。如果你的分支保护要求 GitHub 批准，而审阅者尚未连接 GitHub，编辑器会先要求其连接账号。

发布时只会合并审阅者批准的 branch 版本。如果你在批准后编辑了 branch，请重新请求审阅。GitHub 的合并检查（例如必需的状态检查）仍然适用。

在受保护的 deployment branch 上，admins 无法不经审阅直接发布。直接在 GitHub 中进行的批准不算作编辑器中的批准。

<div id="review-and-merge-pull-requests">

## 审阅并合并 pull request

</div>

当你的分支存在 pull request 时，发布菜单会显示其已更改的文件和审阅状态，例如 **Pull request created**、**Review required**、**Changes requested** 或 **Approved**。如果 Mintlify 托管你的仓库，草稿会显示 **Draft in progress**。如果你的仓库托管在你自己的 Git 提供方（例如 GitHub、GitLab 或 Bitbucket）中，点击 **View request** 可在其中打开该 pull request。

<Tip>
  如果分支仍有未解决的评论线程，发布菜单会显示一条警告，列出未解决评论的数量，以替代 **Ready to publish** 或 **Approved**。你仍然可以合并并发布。该警告用于提醒你先处理反馈。
</Tip>

在 feature branch 上，审阅者会在你的 Git 提供方中批准你的 pull request，或者在 GitHub 上从编辑器中批准。如果你的项目[要求发布前审阅](#require-review-before-publishing)，审阅者则会在编辑器中批准你的更改。请参阅[审阅 branch 上的更改](#review-changes-on-a-branch)。

1. 点击顶部栏中的 **Publish**，然后点击 **Request review**。这会将 pull request 标记为可供审阅。
1. 审阅者在你的 Git 提供方中批准 pull request。如果你的仓库位于 GitHub 且该 pull request 需要批准，审阅者也可以点击页面顶部 **This branch needs a GitHub review** 横幅中的 **Approve**。要从编辑器中批准，审阅者必须[连接其 GitHub 账号](/zh/dashboard/profile#connect-github)。
1. 点击 **Publish**，然后点击 **Merge and publish**。编辑器会合并 pull request，部署你的更改，并把你切换回 deployment branch。

如果 Mintlify 托管你的仓库并且不要求审批，发布菜单会改为显示 **Publish**，一步完成合并和部署。

<Tip>
  在你的 Git 提供方中配置分支保护规则以要求使用 pull request。请参阅 GitHub 帮助中的 [About protected branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)，或 GitLab 帮助中的 [Protected branches](https://docs.gitlab.com/user/project/repository/branches/protected/)。
</Tip>

<div id="compare-changes-before-merging">

### 合并前比较更改

</div>

在发布菜单中点击任意已更改的文件，即可在 diff 视图中将其与已发布版本进行比较。若要退出 diff 视图，请点击顶部栏中的 **Viewing changes**。可视化模式会显示可视化 diff，source 模式会显示文本 diff。无法显示 diff 的文件（例如图片或已删除的文件）会出现在列表中，但无法点击。

在页面或 `docs.json` 的 source 模式 diff 中，在顶部栏中选择 **Unified** 或 **Split**，即可以单列或并排方式显示更改。在你做出选择之前，编辑器会根据窗口宽度选择合适的布局。编辑器会记住你的选择，并应用于之后的 diff。

出现在分支 diff 中的[隐藏页面](/zh/organize/hidden-pages)也可以从发布菜单中打开，即使它们并未出现在站点导航中。

<div id="pull-request-titles-and-descriptions">

### pull request 的标题和描述

</div>

pull request 的标题来自你的分支标题。

如果你的分支存在打开的评论线程，Mintlify 会把这些线程的摘要添加到 pull request 描述中。请参阅[协作](/zh/editor/collaborate#comments)。

<div id="review-an-automation-run">

## 审阅自动化运行

</div>

当[自动化](/zh/automations)打开 pull request 时，在 Slack 通知或通知邮件中点击 **View changes**，即可在该自动化的分支上打开编辑器。编辑器会以 diff 视图打开，[智能体](/zh/editor/agent#continue-an-automation-run)会在旁边打开，并带有该自动化所做工作的上下文。

若要改为打开该自动化的预览部署，请在仪表板 [Automations](https://app.mintlify.com/settings/project/automations?tab=runs) 页面的 **Runs** 标签页中打开该运行，然后点击 **Preview**。
